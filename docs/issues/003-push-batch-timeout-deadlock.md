# [agent-factory] push 훅이 백로그 전체를 한 청크·5초 타임아웃으로 보내다 영구 실패(교착)한다

- **상태**: OPEN (수동 드레인으로 백로그는 해소, 훅 자체 미수정) — 수정 제안 아래
- **대상**: `plugins/agent-factory-plugin/hooks/push-sessions.mjs`
- **발견일**: 2026-08-10
- **심각도**: HIGH — 무음 실패다. 세션 요약 `.md`는 로컬에만 쌓이고 서버 DB(진실의
  원천)에 영영 도달하지 못한다. 게다가 **백로그가 커질수록 실패가 더 확실해지는
  자기강화 교착**이라, 한 번 임계치를 넘으면 훅 단독으로는 절대 회복되지 않는다.

## 증상

세션 요약 파이프라인의 4단계(전송+정리)에서 push 훅이 `exit 0`으로 조용히 끝나는데
서버에는 아무것도 도착하지 않고 로컬 `.md`도 정리되지 않았다. `errors.jsonl` 에만
같은 실패가 **며칠에 걸쳐 반복** 남아 있었다:

```
2026-07-31T00:14:37Z | push | network 실패: TypeError: fetch failed
2026-08-03T02:30:21Z | push | network 실패: AbortError: This operation was aborted
2026-08-04T06:25:11Z | push | network 실패: AbortError: This operation was aborted
2026-08-05T06:18:04Z | push | network 실패: AbortError: This operation was aborted
2026-08-06T09:21:35Z | push | network 실패: AbortError: This operation was aborted
2026-08-10T08:59:34Z | push | network 실패: AbortError: This operation was aborted
```

"network 실패 / AbortError"라 처음엔 서버 다운·네트워크 단절로 보였으나, **조사 시점에
서버는 정상 기동 중이었다**(`127.0.0.1:3001` LISTEN, 단일 요청에 정상 응답). 무언가
다른 원인이 5초 타임아웃을 태우고 있었다.

## 원인

훅은 미전송 `.md`를 모아 `MAX_BATCH` 단위로 **한 번의 POST**에 실어 보내는데, 그
요청에 **레코드 수와 무관한 고정 5초 타임아웃**을 건다. 서버의 레코드당 처리 시간이
누적되면 이 5초를 넘겨 클라이언트가 스스로 요청을 끊는다(AbortError).

```js
const TIMEOUT_MS = 5000;   // :37  요청당 고정 5초
const MAX_BATCH = 50;      // :39  한 POST에 최대 50 레코드

for (let i = 0; i < pending.length; i += MAX_BATCH) {
  const chunk = pending.slice(i, i + MAX_BATCH);
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), TIMEOUT_MS);   // :171-172
  try {
    response = await fetch(`${apiBase}/api/agent-factory/records`, {
      method: "POST",
      body: JSON.stringify({ records: chunk.map((p) => p.payload) }),
      signal: controller.signal,
    });                                                              // :176-184
  } catch (err) {
    appendLog("push", `network 실패: ${err}`);
    break;                 // :187  ← 첫 실패에서 루프 전체 중단
  }
  ...
}
```

핵심 결함은 세 가지가 맞물린다:

1. **배치 크기와 타임아웃이 서로를 모른다.** `MAX_BATCH=50`인데 타임아웃은 레코드
   1건이든 50건이든 똑같이 5초다. 서버가 레코드당 순차로 일하면 배치가 클수록
   반드시 초과한다.
2. **부분 성공을 커밋하지 않는다.** `catch`에서 곧장 `break`하고, abort된 청크는
   상태(state)를 안 찍으므로 **다음 실행에서 처음부터 다시** 같은 크기로 재시도된다.
3. **자기강화 교착.** 실패로 정리가 안 되니 로컬 백로그가 계속 커지고, 백로그가
   클수록 한 청크(≤50)에 담기는 양이 많아져 5초 초과가 더 확실해진다. 임계치를
   넘는 순간 **영구 실패 루프**에 들어간다.

## 실측

같은 서버·같은 설정에서 요청 규모만 바꿔 측정했다.

| # | 요청 | 페이로드 | 결과 |
|---|---|---|---|
| 1 | 빈/오형식 본문 1건 | ~10 B | HTTP 400 즉시(~0.2 ms) — 연결·인증 정상 |
| 2 | 실제 레코드 **1건**(가장 큰 `.md`) | 12.6 KB | **HTTP 200, 1,368 ms**, `outcome: updated` |
| 3 | 훅 정식 실행(백로그 **38건**, 1청크) | — | **AbortError @ 5,000 ms** — 서버 미완료 |

레코드당 약 1.3초이므로 38건이면 순차 처리에 ~50초가 필요하다. 5초 타임아웃은
**7건 남짓**에서 이미 넘어간다. 즉 백로그가 대략 한 자릿수 후반을 넘는 순간부터
훅은 구조적으로 성공할 수 없다.

## 재현 절차

1. 서버가 잠시 느리거나 내려가 push가 몇 번 실패해, 미전송 `.md`가 ~10건 이상 쌓이게 둔다.
2. 서버를 정상화한 뒤 push 훅을 실행한다.
3. 서버가 응답 가능한데도 `errors.jsonl`에 `AbortError`가 남고, 로컬 `.md`는 그대로다.
4. 다시 실행해도 같은 실패가 반복된다(백로그가 줄지 않으므로).

## 조치 (이번 인시던트)

훅 파일(플러그인 캐시)은 건드리지 않고, **훅과 동일한 페이로드·정리 규칙**을 그대로
따르는 일회성 드레인을 수행했다.

- 미전송 `.md` 38건을 **5건씩 청크**로, **30초 타임아웃**으로 `POST /api/agent-factory/records`
  에 보냈다(페이로드: `markdown`·`fileName`·`projectPath`·`projectName` + git 신원/리모트 보강 + `metrics`).
- 서버가 `outcome: created|updated|unchanged`로 확인한 레코드만 로컬 `.md`·`metrics.json`을 삭제했다.
- 결과: **38/38 전달·정리 완료, 남은 미전송 0건.** 서버는 커밋 sha + revision으로
  멱등 처리하므로 중복 전송 위험은 없다.

부수로, 신호 섹션 포맷 경고(`극성을 가진 불릿을 찾지 못했다`) 4건이 있었다 — 요약
작성 시 이모지를 볼드 밖(`🔴 **부정**`)에 둬 서버 파서의 기대 형식
(`- **🔴 부정(출력):**`, 볼드가 이모지를 감쌈)과 어긋난 것. 규격에 맞춰 재작성·재전송해
경고 0건으로 마무리했다. 이 파서 규약은 산출물 작성 규칙에 명시하는 편이 좋다.

## 수정 방향 (제안)

원인 1·2·3에 각각 대응한다. 개별로도 완화되지만 **함께** 적용해야 교착이 끊긴다.

- **A. 타임아웃을 배치 크기에 비례시킨다.** `TIMEOUT_MS = base + perRecord × chunk.length`
  형태(예: 기본 5s + 레코드당 2s). 서버의 순차 처리 특성을 클라이언트가 인정하는 셈이다.
- **B. 부분 성공을 커밋한다.** 첫 실패에서 `break`하되, **직전까지 성공한 청크의 상태는
  이미 찍혀 정리된다**(현재도 청크별로 상태를 찍는 구조이면 유지). 최소한 성공 청크의
  로컬 정리가 실패 청크 때문에 롤백되지 않게 해, 매 실행이 백로그를 **단조 감소**시키게 한다.
- **C. 배치를 잘게 쪼갠다.** `MAX_BATCH`를 5~10으로 낮춘다. A 없이도 한 청크가 5초에
  들어올 확률이 커지고, B와 합치면 큰 백로그도 여러 번의 실행에 나눠 확실히 비운다.

**B + C 를 최소 조합으로 권장한다.** C가 한 청크를 타임아웃 안에 들여보내고, B가 매
실행마다 백로그를 줄여 교착을 원천 차단한다. A는 서버가 느려질 때의 여유로 더한다.

추가로 고려할 것:

- **실패를 관측 가능하게.** 지금은 `errors.jsonl`에만 남아 사용자가 열어보지 않으면
  모른다(002와 같은 무음 실패 계열). "미전송 N건이 며칠째 쌓임" 같은 상태를 드러내는
  신호가 필요하다.
- **서버측 배치 처리 병렬화/트랜잭션.** 레코드당 ~1.3초는 순차 DB 쓰기로 보인다.
  배치를 한 트랜잭션·벌크 삽입으로 처리하면 per-record 비용이 크게 줄어 근본이 완화된다.
- **AbortError 메시지 개선.** "network 실패"로 뭉뚱그리면 서버 다운으로 오인된다.
  타임아웃(abort)과 연결 실패(fetch failed)를 구분해 로깅하면 진단이 빨라진다.

## 영향 범위 메모

이 결함은 **서버가 잠깐이라도 불안정했던 이력이 있는 모든 환경**에서 잠복한다. 한 번
백로그가 임계치를 넘으면 이후 서버가 완전히 정상이어도 훅이 스스로 회복하지 못하고,
로컬에는 전송된 적 없는 요약이 무한정 쌓인다. 모니터링 도구로서 데이터가 **틀린 게
아니라 도달하지 못하는데, 그 사실이 드러나지 않는** 방식의 실패다.
