# MFE 경계 설계 기준

마이크로 프론트엔드의 비용은 **런타임 통합**에서 나온다(버전 협상·Provider 중복·전역 상태
브리지·배포 조합 폭발). 그래서 경계는 "코드가 커서" 긋는 것이 아니라 **그 비용을 지불할
이유가 있을 때만** 긋는다.

> 📎 실제 판단 사례(무엇을 쪼갰고 무엇을 합쳤는지, 그 결과)는 같은 폴더의
> [`examples.md`](./examples.md)에 있다.

---

## 1. 경계를 긋는 유일하게 타당한 기준

**모듈 = 독립 배포 단위 = 소유 팀 단위.** 이 셋이 일치하지 않으면 경계가 아니다.

| 판단 | 신호 |
|---|---|
| **떼어낼 만하다** | 다른 팀이 소유한다 · 릴리스 주기가 다르다 · 장애가 나도 나머지 화면은 살아야 한다 · 다른 기술 스택 전환을 실험한다 |
| **떼면 손해다** | 같은 팀이 같은 주기로 배포한다 · 두 화면이 같은 상태를 실시간으로 공유한다 · 한쪽만 배포하면 반드시 깨진다 · "폴더가 커져서" 가 유일한 이유다 |

한 팀이 모든 모듈을 배포한다면 그것은 마이크로 프론트엔드가 아니라 **복잡한 코드 분할**이다.
이 경우 이미 쪼개진 구조를 유지하는 것과 합치는 것 중 무엇이 싼지 따로 판단한다
(이미 돌아가는 구성을 되돌리는 비용도 실재한다).

---

## 2. 셸(Host)이 소유해야 하는 것

원격 모듈로 넘기면 안 되는 것들이다. 넘기는 순간 모듈마다 중복되고 서로 어긋난다.

- **전역 레이아웃** — 헤더·사이드바·브레드크럼 셸
- **라우팅 트리** — 경로 정의(`pathKeys`)와 메뉴 구성. 원격 모듈은 자기 경로를 모른다
- **인증·권한·메뉴 데이터** — 셸이 받아 전역 스토어에 채우고, 모듈은 읽기만 한다
- **테마·언어의 원본 상태** — 모듈은 이벤트를 구독해 따라간다
- **원격 로딩 정책** — `Suspense` 폴백, 에러 폴백, 재시도

반대로 **모듈이 소유하는 것**: 자기 도메인의 화면·상태·서버 호출·i18n 리소스·CSS.
"이 도메인 화면 안에서만 의미 있는 것"은 전부 모듈 쪽이다.

---

## 3. 노출 입도 — 페이지인가 위젯인가

한 모듈이 무엇을 `exposes` 할지는 **실패했을 때 무엇이 사라져야 하는가**로 정한다.

| 입도 | 노출하는 것 | 실패 시 | 쓰는 곳 |
|---|---|---|---|
| **페이지** | 라우트 하나를 통째로 채우는 컴포넌트 | 그 화면만 에러 화면 | 메뉴에 대응하는 도메인 화면 |
| **위젯** | 카드·차트 등 화면 조각 | 그 카드 자리만 작은 에러 박스 | 대시보드처럼 여러 모듈을 한 화면에 모으는 곳 |

규칙:

- **기본은 페이지 단위다.** 위젯 노출은 "여러 모듈의 조각을 한 화면에 모아야 한다"는
  요구가 실제로 있을 때만 만든다.
- 위젯을 노출하면 **셸의 폴백 정책에 그 id 를 등록**해야 한다(등록을 잊으면 카드 하나
  때문에 대시보드 전체가 에러 화면이 된다).
- 노출 개수가 늘수록 계약면이 넓어진다. **한 화면당 하나**를 넘겨 잘게 노출하지 않는다
  (모달·탭 각각을 노출하는 식은 계약 폭발의 시작이다).

---

## 4. 모듈 간에 무엇을 어떻게 주고받는가

경로는 넷뿐이다. 각각 허용 조건이 다르다.

| 경로 | 용도 | 허용 조건 |
|---|---|---|
| **서버 API** | 도메인 데이터 | 기본값. 다른 모듈의 데이터가 필요하면 원칙적으로 서버에서 받는다 |
| **전역 스토어(`window`)** | 인증·메뉴 권한처럼 **셸이 쓰고 모두가 읽는** 소수의 값 | 쓰기 주체가 셸 하나여야 한다. 모듈이 쓰기 시작하면 추적 불가능해진다 |
| **CustomEvent** | 테마·언어처럼 **방향성 있는 알림** | 구독 해제를 반드시 짝으로 둔다. 이벤트 이름은 상수로 공유한다 |
| **공유 라이브러리(`shared`)** | react·router·query 등 인스턴스가 하나여야 하는 것 | 양쪽 `singleton` 정렬 필수. 여기에 도메인 상태를 태우지 않는다 |

**금지에 가까운 것**:

- **Remote → Remote 직접 참조.** 두 모듈이 서로를 `loadRemote` 하면 배포 순서에 사이클이
  생기고, 한쪽 장애가 양쪽을 죽인다. 필요하면 셸이 중개한다.
- **셸이 모듈 내부 상태를 읽는 것.** 셸은 모듈에 props 를 내려줄 수는 있어도 모듈 안을
  들여다보지 않는다.
- **공유 라이브러리에 도메인 상태 얹기.** `zustand` 를 공유해도 store 인스턴스는 공유되지
  않는다(라이브러리 코드만 공유된다). 진짜 공유가 필요하면 그건 §1 기준상 **한 모듈이어야
  한다는 신호**다.

## 5. 공통 코드를 두는 곳

| 대상 | 두는 곳 |
|---|---|
| 타입·계약 | 공용 **타입 패키지**로 배포하고 `shared.singleton` 으로 정렬 |
| 공용 UI 컴포넌트 | 공용 **컴포넌트 라이브러리 패키지**(npm). 모듈이 각자 의존하며, 자체 Provider 를 마운트하는 설계라면 `singleton: false` 로 사본을 허용하는 편이 안전하다 |
| 도메인 로직 | **복제하지 말고** 소유 모듈 하나에 둔다. 두 모듈이 같은 도메인 로직을 필요로 하면 경계가 잘못 그어진 것이다 |
| 빌드·lint 설정 | 템플릿 저장소 + 일괄 업데이트 스크립트 |

## 6. 새 화면이 생겼을 때 — 판단 순서

```
1. 이 화면의 소유 팀·배포 주기가 기존 모듈 중 하나와 같은가?
   → 같다  : 그 모듈에 넣는다. (기본값)
   → 다르다: 2로.
2. 독립 배포가 실제로 필요한가(다른 주기로 릴리스할 것인가)?
   → 아니다: 가장 가까운 모듈에 넣는다.
   → 맞다  : 3으로.
3. 새 모듈의 초기 비용을 감당하는가?
   (설정·env·포트·CI·Host 등록·계약 문서·모니터링)
   → 아니다: 기존 모듈에 넣고, 분리 조건이 충족되면 그때 뗀다.
   → 맞다  : 새 Remote 를 만든다.
4. 노출 입도를 정한다(§3). 기본은 페이지 하나.
5. 이 모듈이 필요로 하는 전역 전제를 셸이 제공하는지 확인한다(§2·§4).
```

**"나중에 분리하기 어려우니 미리 쪼갠다"는 근거로 모듈을 만들지 않는다.** 한 모듈 안의
도메인 폴더를 나중에 Remote 로 승격하는 비용은, 처음부터 잘못 그은 경계를 되돌리는
비용보다 훨씬 작다.

---

## 7. 경계가 잘못됐다는 신호

- 한 기능을 고치는 데 **두 개 이상 모듈을 함께 배포**해야 한다 → 경계가 기능을 가로지른다
- 모듈 간 `window` 브리지가 계속 늘어난다 → 원래 한 모듈이어야 한다
- 모듈 A 가 모듈 B 의 노출 컴포넌트를 부른다 → 셸 중개로 바꾸거나 합친다
- 같은 도메인 타입이 여러 모듈에 복제돼 있다 → 타입 패키지로 올린다
- 셸이 특정 모듈의 내부 상태를 알아야 화면이 맞는다 → 그 화면은 셸 소유다
- 노출 키가 한 모듈에서 수십 개로 늘었다 → 입도가 너무 잘다(§3)
