# MFE 경계 설계 — 판단 사례집

`SKILL.md` 의 기준을 실제 상황에 적용한 사례다. 판단이 갈릴 때 읽는다.

---

## 사례 1 — 도메인별 Remote + 레이아웃 셸 (기본 구성)

**상황**: 관리 포털 하나에 문서·인프라·에이전트·모델·워크플로·어시스턴트 등 성격이 다른
도메인이 계속 추가된다. 도메인마다 담당이 다르고 릴리스 주기도 다르다.

**결정**: 셸(레이아웃) 1개 + 도메인 Remote N개.

- 셸: 사이드바·메뉴·라우팅 트리·인증/권한 스토어·테마/언어 원본·원격 로딩 정책
- 각 Remote: 자기 도메인 화면 전부 + 자체 상태·서버 호출·i18n·CSS

**근거**: §1 의 세 신호(소유 팀·릴리스 주기·장애 격리)가 모두 성립한다. 인프라 모듈이
죽어도 문서 화면은 살아야 한다는 요구가 실재했다.

**대가**: 모듈이 늘 때마다 `shared` 정책을 전 모듈에 맞춰야 하고, 공용 컴포넌트 라이브러리
업그레이드가 전 모듈 동시 작업이 된다(일괄 업데이트 스크립트로 흡수).

---

## 사례 2 — 대시보드 카드만 위젯으로 노출

**상황**: 셸의 통합 대시보드에 에이전트·모델·인프라의 상태 카드를 나란히 놓아야 한다.
각 카드의 데이터·계산은 해당 도메인 모듈이 소유한다.

**후보**:
- (A) 셸이 각 도메인 API 를 직접 호출해 카드를 그린다
- (B) 각 모듈이 카드 컴포넌트를 **위젯으로 노출**하고 셸이 배치만 한다

**결정**: B.

**근거**: A 는 도메인 계산 로직을 셸에 복제한다(§7 "같은 도메인 로직 복제" 신호).
B 는 계약면이 늘지만, 카드 하나가 죽어도 나머지가 살아남는 폴백을 줄 수 있다(§3).

**필수 조건**: 노출한 위젯 id 를 셸의 폴백 정책에 **등록**한다. 등록하지 않으면 카드 하나
실패가 전체 화면 에러로 번진다.

---

## 사례 3 — "이 화면 커졌으니 모듈로 뺄까요"

**상황**: 한 모듈 안의 특정 도메인 폴더가 커져 빌드가 느려졌다. 담당은 같은 팀이고
배포도 늘 함께 나간다.

**결정**: 떼지 않는다. 코드 분할(lazy route)과 빌드 캐시로 해결.

**근거**: §1 — 같은 팀·같은 주기면 경계가 아니다. 떼는 순간 `shared` 정렬·env·포트·CI·
Host 등록·계약 문서·모니터링이 새로 생기는데, 얻는 것은 빌드 시간뿐이다.

**뗄 조건을 명시해 둔다**: "이 도메인을 다른 팀이 맡거나, 다른 주기로 릴리스하게 되면 뗀다."

---

## 사례 4 — 두 모듈이 같은 상태를 실시간으로 봐야 한다

**상황**: 배포 진행 상황을 A 모듈의 화면과 B 모듈의 알림 패널이 동시에 반영해야 한다.

**후보**:
- (A) `window` 브리지로 상태를 공유
- (B) 서버(SSE/폴링)를 단일 출처로 두고 양쪽이 각자 구독
- (C) 두 화면을 한 모듈로 합친다

**결정**: B. 이미 서버가 상태의 원본이므로 프론트에서 다시 공유할 이유가 없다.

**A 를 피한 이유**: 브리지는 쓰기 주체가 둘이 되는 순간 추적이 불가능해진다(§4).
브리지가 계속 늘어난다면 그것은 §7 의 "원래 한 모듈이어야 한다"는 신호다.

**C 를 택했을 상황**: 두 화면이 서버를 거치지 않는 UI 상태(선택·필터·드래그 중인 항목)를
공유해야 했다면 합치는 것이 맞다.

## 사례 5 — Remote 가 Remote 를 부르고 싶다

**상황**: 에이전트 모듈의 화면 안에서 워크플로 모듈의 편집기를 띄우고 싶다.

**결정**: 셸이 중개한다. 에이전트 모듈은 "편집기를 열어달라"는 요청을 셸에 올리고
(라우팅 이동 또는 이벤트), 셸이 워크플로 모듈을 로드해 띄운다.

**근거**: 직접 참조는 배포 사이클에 순환을 만든다 — 워크플로 배포가 에이전트 화면을
깨뜨릴 수 있고, 그 사실이 에이전트 모듈의 계약 어디에도 드러나지 않는다.

**예외**: 정말 강하게 결합돼 있다면 §1 기준상 **한 모듈이어야 한다**는 신호로 읽는다.

## 사례 6 — 공용 컴포넌트 라이브러리를 singleton 으로 둘까

**상황**: 공용 React 컴포넌트 라이브러리를 셸과 모든 모듈이 쓴다.

**결정**: `singleton: false`(사본 허용). 대신 버전은 일괄 업데이트 스크립트로 정렬한다.

**근거**: 이 라이브러리는 각 앱이 자체 Provider 를 마운트하는 설계다. singleton 으로 묶으면
한 모듈의 Provider 트리에 다른 모듈이 얹히는 상황이 생겨 포털·토스트가 엉킨다.
반면 `react`·`react-dom`·라우터·쿼리는 **인스턴스가 하나여야 동작하므로** singleton 이 필수다.

**규칙화**: "Context 를 통해 앱 전역에 하나만 존재해야 하는가"가 singleton 판단 기준이다.
컴포넌트를 그리기만 하는 라이브러리는 사본이 있어도 된다.

---

## 사례 7 — 노출 키가 열세 개가 됐다

**상황**: 한 모듈이 페이지 8개 + 위젯 5개를 노출하게 됐다.

**판정**: 아직 정상 범위. 페이지 노출은 그 모듈이 담당하는 **메뉴 개수만큼** 늘어나는 것이
자연스럽다(§3 "한 화면당 하나").

**경고 신호는 개수가 아니라 입도다**: 한 화면 안의 모달·탭·폼을 각각 노출하기 시작하면
계약면이 폭발한다. 그런 조각은 모듈 내부에 두고 화면 단위로만 노출한다.

**동반 조치**: 노출이 늘수록 계약 문서(`MFE_{RemoteName}` 스킬)의 가치가 커진다.
셸 개발자가 기억으로 노출 키를 타이핑하는 순간 오타 사고가 난다.
