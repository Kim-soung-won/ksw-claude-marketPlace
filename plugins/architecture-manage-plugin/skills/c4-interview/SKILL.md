# C4 인터뷰 모델링

사용자와 여러 턴에 걸쳐 질의응답을 주고받으며 C4 아키텍처 JSON을 점진적으로
완성한다. 아래 지침은 인터뷰가 끝날 때까지 세션 전체에 적용되는 상시
지침이다 — 매 사용자 답변 턴마다 "갱신 → 커버리지 체크 → 다음 질문" 루프를
반복한다.

## 1. 초기화 (첫 턴에만)

1. 작업 대상 JSON 파일을 결정한다. 인자: `$target`
   - 기존 파일 경로면 그 파일을 대상으로 한다.
   - 프로젝트명이면 프로젝트 루트에 `<프로젝트명>-c4-model.json`을 새로 만든다.
   - 인자가 비어 있으면 프로젝트명(또는 이어서 작업할 파일 경로)을 먼저 묻는다.
2. 스키마 스펙과 technology 카탈로그 id 규칙은
   `${CLAUDE_PLUGIN_ROOT}/resources/c4-model/schema-spec.md`를 Read해서
   그대로 따른다. 이 스킬에는 스펙을 중복 기술하지 않는다 — 그 파일이
   단일 소스다.
3. 대상 파일이 이미 존재하면 Read해서 현재 채워진 정도를 파악하고,
   아래 커버리지 표를 먼저 제시한 뒤 빈 곳부터 이어서 인터뷰한다.
   존재하지 않으면 4개 최상위 배열이 모두 빈 배열인 골격 JSON을 먼저 저장한다.
   소스 분석 결과(c4-schema-generator 출력 등)를 초안으로 받았다면 그 초안을
   대상 파일로 삼아 같은 방식으로 이어간다.

## 2. 단계별 인터뷰 루프

C4 레벨 순서로 진행한다:

1. **시스템 레벨**: 본 시스템은 무엇인지, 사용자/외부 시스템/액터는 누구인지,
   서로 어떻게 통신하는지
2. **컨테이너 레벨**: 각 시스템의 배포 단위(웹앱, API 서버, DB, 워커 등)와
   구현 언어·프레임워크·DB 엔진
3. **컴포넌트 레벨**: 각 컨테이너의 내부 모듈과 책임, 모듈 간 호출 관계
4. **코드 레벨**: 사용자가 원할 때만 (핵심 클래스/함수/인터페이스)

질문 규칙:

- 한 턴에 질문은 **3~5개 이하**로 묶는다. 한꺼번에 전부 묻지 않는다.
- 선택지가 명확한 질문(DB 엔진, 언어/프레임워크, 통신 프로토콜 등)은
  **AskUserQuestion 도구**로 묻는다. 선택지는 technology 카탈로그 id에
  매핑 가능한 값으로 구성한다.
- 서술형 질문(시스템의 역할, 모듈의 책임 등)은 일반 텍스트로 묻는다.
- "모른다", "나중에"라는 답변은 해당 항목을 건너뛰고 커버리지 표에 남겨둔다.

## 3. 매 턴 JSON 갱신

사용자 답변을 받을 때마다:

1. 답변을 스펙에 맞는 노드/connection으로 변환해 **즉시 대상 JSON 파일에
   반영하고 저장**한다. 턴을 넘겨 모아두지 않는다.
2. `position`은 schema-spec.md의 "position 배치 (레이어드 흐름 배치)"
   규칙을 그대로 따른다: 호출 흐름이 왼쪽→오른쪽으로 읽히게 레이어를 나누고
   (레이어 간 x 400, 레이어 내 y 250, 세로 중앙 정렬). 인터뷰로 노드가
   점진적으로 추가되므로, **새 노드를 넣거나 connection이 새로 생겨 흐름이
   바뀔 때마다 해당 레벨(같은 부모) 전체의 position을 다시 계산해** 배치가
   흐트러지지 않게 유지한다.
3. technology는 카탈로그 id와 정확히 일치하는 소문자 값만 쓰고, 카탈로그에
   없는 기술은 가장 가까운 상위 id + `name`/`description`에 구체 기술명을
   적는다 (schema-spec.md의 적용 규칙 그대로).

## 4. 커버리지 체크와 다음 질문 생성

저장 직후 매번 빈 곳을 점검해 표로 보여준다:

```
| 빈 곳 유형                       | 해당 노드 |
|----------------------------------|-----------|
| technology 없음                  | ...       |
| description 없음                 | ...       |
| connection이 하나도 없음         | ...       |
| 컨테이너가 없는 시스템           | ...       |
| 컴포넌트가 없는 컨테이너 (선택)  | ...       |
```

그리고 그 빈 곳을 채우는 질문을 다음 턴에 던진다. 표가 비거나 사용자가
완료를 선언할 때까지 이 루프를 반복한다.

## 5. 완료 조건과 최종 검증

모든 노드에 technology(식별 가능한 경우)와 description이 있고 사용자가
"됐다"고 하면 최종 검증을 수행한다:

```
최종 검증:
- [ ] JSON 파싱 성공 (python3 -m json.tool <파일>)
- [ ] 4개 최상위 배열(systems/containers/components/codeElements) 모두 존재
- [ ] 모든 id가 모델 전체에서 고유
- [ ] 모든 systemId/containerId/componentId/targetId가 실존 노드 id를 참조
- [ ] connection은 같은 레벨 노드끼리만 연결
- [ ] 모든 노드에 connections 배열 존재 (없으면 [])
```

검증 실패 항목은 수정 후 재검증한다. 전부 통과하면 완료 요약을 보고한다:
저장 경로, 레벨별 노드 개수, 주요 technology id 목록, 인터뷰에서 확인하지
못해 비워둔 항목.
