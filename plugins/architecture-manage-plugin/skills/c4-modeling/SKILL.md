# C4 대화형 모델링 (in-session)

아키텍처 모델링은 **여러 턴의 대화 자체가 자산**이다. 이 스킬은 서브에이전트로
컨텍스트를 분리하지 않고 **메인 세션 안에서** 읽은 자료·모든 문답·중간 판단을
컨텍스트에 쌓아가며 이어간다. 아래 지침은 완료할 때까지 세션 전체에 상시 적용된다 —
매 사용자 답변 턴마다 "**갱신 → 저장 → 커버리지 체크 → 다음 질문**" 루프를 돈다.

스키마·technology 카탈로그·position·deployment 규칙은 **`reference/schema-spec.md`를
먼저 Read**해서 그대로 따른다(권위 소스는 거기서 가리키는 `.claude/schema/`). 이
파일에는 스펙을 중복 기술하지 않는다.

## 1. 초기화 (첫 턴에만)

1. **대상 파일 결정** (`$target`): 기존 경로면 그 파일, 이름이면
   `<이름>-c4-model.json`을 만든다. 비어 있으면 이름/경로를 먼저 묻는다.
   기존 파일이면 Read해 현재 채워진 정도를 커버리지 표로 먼저 보여준다.
   없으면 4개 배열이 빈 골격 JSON을 먼저 저장한다.
   - **`designIntent`를 먼저 복원한다**: 파일에 `designIntent`가 있으면 그
     `nextStep`·`openQuestions`·`decisions`를 읽어 "지난번 어디서 멈췄고 무엇이
     미결인지"를 사용자에게 한 줄로 브리핑한 뒤 그 지점부터 이어간다. 이미
     내려진 결정을 다시 묻지 않는다.
2. **읽을 자료 확인** (`$source` 또는 대화): 사용자가 자료를 지정했으면 2단계로,
   아니면 3단계(대화)로 바로 간다. **자료 없이 아키텍처를 지어내지 않는다.**
3. **상대가 누구인지 파악**(페르소나) — 명시 안 하면 첫 질문에서 가볍게 확인한다.
   그 사람 언어로 시작해 C4 개념으로 번역한다:

   | 페르소나 | 입력 언어 | 주 진입 레벨 | 매핑 |
   |---|---|---|---|
   | 고객/사용자 | "이런 걸 하고 싶다", 상대하는 서비스 | Context | 액터(users)·외부 시스템·경계 |
   | 기획자 | 기능·범위·외부 연동 | System+Container | 시스템/외부시스템·배포단위 |
   | 디자이너 | 화면·사용자 플로우 | Container(프론트)+흐름 | 프론트 컨테이너·화면흐름→connection |
   | 개발자 | 기술스택·모듈·통신 | Container/Component | 기술·모듈·프로토콜 |
   | 인프라/운영 | 서버·클러스터·환경·레플리카 | **Deployment** | environment→node→instance |

## 2. 자료 읽기 (자료가 지정된 경우)

입력 소스의 종류에 맞게 세션에서 직접 읽어 초안을 만든다. 전체를 낱낱이 읽지 말고
구조가 드러나는 부분에 집중한다:

- **코드 저장소**: 디렉터리 트리(node_modules·.git 제외), 빌드/의존성 설정, 인프라
  설정(docker-compose·Dockerfile·k8s → deployment 초안의 핵심), 진입점·라우터, README
- **문서/스펙**(기획서·PRD·ADR): 시스템 경계·액터·구성요소·상호작용을 서술에서 추출
- **API 스펙**(OpenAPI/GraphQL): 서비스·엔드포인트 그룹 → 컨테이너/컴포넌트, 외부 연동 → 외부 시스템
- **인프라/배포 설정**: 서비스·DB·브로커 → 컨테이너, 배포 토폴로지 → deployment 레이어 초안

읽어 파악한 내용을 스펙에 맞는 노드로 변환해 **대상 파일에 저장**한다. 자료에 없는 것은
추측하지 말고 비워 두고, 무엇이 비었는지 커버리지 표에 남겨 3단계 대화로 채운다.

## 3. 대화 루프

C4 레벨 순서(system→container→component→code)를 기본으로 하되, **페르소나의 진입
레벨에서 시작**해 자연스럽게 인접 레벨로 넓힌다. 물리(deployment)는 운영/개발
페르소나거나 사용자가 배포를 말할 때 별도 트랙으로 다룬다.

질문 규칙:
- 한 턴에 **3~5개 이하**로 묶는다. 한꺼번에 다 묻지 않는다.
- 선택지가 명확한 질문(DB 엔진, 언어/프레임워크, 프로토콜, nodeType 등)은
  **AskUserQuestion**으로 묻고, 선택지는 카탈로그 id에 매핑 가능하게 구성한다.
- 서술형(역할·책임)은 일반 텍스트로 묻는다.
- "모른다/나중에"는 건너뛰고 커버리지 표에 남긴다.

## 4. 매 턴 JSON 갱신

사용자 답변마다:
1. 답변을 스펙에 맞는 노드/connection/deployment 노드로 변환해 **즉시 대상 파일에
   저장**한다. 턴을 넘겨 모으지 않는다.
1-b. **설계 의도(`designIntent`)를 함께 기록한다 — 로그가 아니라 자산이다.**
   - 무언가를 "이렇게 하기로" 정할 때마다 `decisions`에 `{topic, choice, why,
     rejected?, relatedIds?}`로 남긴다. **`why`(이유)는 필수** — 이유 없이 정한
     것은 아직 결정이 아니다. 대안을 저울질했다면 기각한 쪽을 `rejected`에 남긴다.
   - 사용자가 낯선 도메인 용어를 쓰면 `glossary`에 그의 말 그대로 담는다.
   - 아직 못 정한 것은 `openQuestions`에, **의도적으로 범위 밖인 것**은
     `outOfScope`에(= "모름"이 아니라 "안 함"). 매 턴 끝에 `nextStep`을 갱신한다.
   - 이 정보는 앱의 Design Intent 드로어에 그대로 보이고 편집되므로, 사용자가
     읽을 것을 전제로 명확하게 쓴다.
2. position은 `reference/schema-spec.md`의 "레이어드 흐름 배치" 규칙을 따르고, 새
   노드·연결로 흐름이 바뀌면 그 레벨 전체 position을 다시 계산한다. (deployment의
   position은 앱이 자동 레이아웃하므로 대략값이어도 된다.)
3. technology는 카탈로그 id와 정확히 일치하는 값만. 없으면 가장 가까운 상위 id +
   `name`/`description`에 구체명.

## 5. 커버리지 체크

저장 직후 매번 빈 곳을 표로 보여주고, 그 빈 곳을 채우는 질문을 다음 턴에 던진다:

```
| 빈 곳 유형                       | 해당 노드 |
|----------------------------------|-----------|
| technology 없음                  | ...       |
| description 없음                 | ...       |
| connection이 하나도 없음         | ...       |
| 컨테이너가 없는 시스템           | ...       |
| 컴포넌트가 없는 컨테이너 (선택)  | ...       |
| deployment 미구성 (선택)         | ...       |
| 이유(why) 없는 결정              | ...       |
```

표가 비거나 사용자가 완료를 선언할 때까지 반복한다. 여러 페르소나가 한 파일을 이어서
채울 수 있다(고객이 Context → 기획자가 컨테이너 → 개발자가 컴포넌트 → 운영이 deployment).

## 6. 완료 조건과 최종 검증

사용자가 "됐다"고 하면 **번들 검증기로** 검증한다(눈으로 체크하지 말고 기계로):

```bash
node ${CLAUDE_PROJECT_DIR}/.claude/schema/validate.mjs <대상파일.json>
```

id 고유성·계층 참조·connection 동일 레벨·connections 배열·deployment 3계층 부모
규칙·containerInstance container 참조까지 강제한다. **exit 0(PASS)**가 나올 때까지
수정·재검증한 뒤 완료 요약을 보고한다: 저장 경로, 레벨별 노드 개수(+deployment),
주요 technology id, 인터뷰에서 확인 못 해 비워둔 항목.
