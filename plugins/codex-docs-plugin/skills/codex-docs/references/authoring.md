# 작성과 검증

## 스킬

사용자의 실제 요청을 나타내는 짧은 name·description을 작성한다. 공통 판단은 SKILL.md,
조건부 상세는 상대 링크로 연결한 references에 둔다. 사용할 이유가 없는 빈 디렉터리나
예제 파일을 만들지 않는다. 실행 환경에 없는 도구 호출을 지시하지 않는다.

프로젝트 스킬, 개인 스킬, 배포 플러그인 중 요청한 범위에 쓴다. 기존 스킬을 고칠 때는
트리거와 참조 파일도 확인한다. frontmatter·이름·링크를 검사하고, 스크립트가 있으면
대표 입력으로 실행한다. 자동 선택과 실제 작업 결과는 별도 사용 시험으로 확인한다.

## 커스텀 에이전트

격리된 작업이 필요한지 먼저 판단한다. 규약 재사용만 필요하면 스킬로 충분할 수 있다.
공식 문서의 현재 TOML 필드로 이름·트리거·작업 지시를 정의하고, 모델은 요청이나 명확한
이유가 없으면 상속한다. 권한과 작업 디렉터리, 리소스 접근 경로가 실제 환경에서 맞는지 확인한다.

Claude의 YAML tools/model/color를 그대로 복사하지 않는다. 읽기 전용 감사와 테스트 실행에
필요한 쓰기 권한이 충돌하면 감사와 실행을 분리하거나 실행 미검증을 보고한다.
플러그인 안에 에이전트 파일을 넣었다는 이유만으로 자동 등록됐다고 말하지 않는다.

## 플러그인·마켓플레이스

공식 패키징 규격과 저장소 규약을 함께 확인한다. 매니페스트 이름·폴더명·카탈로그 항목,
source의 기준 디렉터리, 스킬·MCP·자산 참조가 실제로 존재하는지 검사한다.
다른 제품용 매니페스트가 공존하면 공통 메타데이터와 제품별 필드를 구분한다.

등록 도구가 제공되면 사용한다. 카탈로그의 기존 이름·순서·정책을 보존한다. 설정 위치와
설치 범위를 혼동하지 않는다. 버전·CHANGELOG·갱신 절차를 맞춘 뒤 실제 지원 클라이언트에서
발견·설치·새 세션 호출을 확인한다. 설치할 환경이 없으면 정적 검증 범위를 보고한다.

## 설정·MCP·훅

적용 범위와 설정 우선순위를 확인한 뒤 관련 항목만 수정한다. 권한 완화가 진단의 기본 해법이
되지 않게 한다. MCP는 전송 방식·환경 변수·인증·연결 상태를 나누어 확인한다.
훅은 현재 이벤트 스키마와 matcher를 근거로 작성하고, 외부 부작용 없는 샘플 입력으로
입출력과 실패 동작을 검증한 뒤 실행 환경에서 확인한다. 문서의 예제 명령을 사용자의
실제 서버 주소나 자격 증명이라고 가정하지 않는다.
