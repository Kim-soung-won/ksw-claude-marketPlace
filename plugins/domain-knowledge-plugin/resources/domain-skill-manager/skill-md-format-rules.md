# domain-skill-manager — SKILL.md 포맷 규칙

> 이 파일은 같은 디렉터리의 `procedure.md`에서 분리된 정적 참고 자료다.
> 본문(워크플로 로직)과 분리해 4단계(SKILL.md 작성)에 진입했을 때만
> 읽는다. 결과 리포트 출력 형식은 같은 디렉터리의 `result-output-format.md`를 참고한다.

---

## Frontmatter

```yaml
---
name: {도메인}_{타입}
description: >-
  {아래 "description 작성 규칙"에 따라 타입별 패턴으로 작성}
metadata:
  type: domain-skill
  collaborators:          # 협업자가 있는 경우만 포함
    - {이름} ({역할/팀})
  confidence:             # NEW — 지식 확신도 추적
    unconfirmed:          # 협업자 확인이 아직 안 된 항목
      - topic: "{무엇이 불확실한가}"
        note: "{왜 불확실하고, 무엇을 확인해야 하는가}"
    inferred:             # 코드·문서에서 추론한 항목 (직접 확인 안 됨)
      - topic: "{추론한 내용}"
        note: "{어디서 추론했는가}"
---
```

**`confidence` 섹션 작성 기준**:

| 분류 | 언제 사용 |
|------|-----------|
| `confirmed` (기본) | 협업자가 직접 말한 내용. 별도 표기 없음 (스킬 본문이 곧 confirmed) |
| `unconfirmed` | 입력에 "확인 필요", "아직 모름", "추정"이 포함된 경우. 기존 TODO 주석 대체 |
| `inferred` | 협업자 발언 없이 코드나 타 스킬에서 추론한 내용 |

`unconfirmed` 항목이 있으면 body 섹션의 해당 부분에 `⚠️ unconfirmed` 주석으로 위치를 표시한다:

```markdown
| `schemaUsed` | `{ id, name }[] \| null` | ⚠️ unconfirmed: 단수/복수 미확인 |
```

## description 작성 규칙

> **description은 스킬 자동 호출의 트리거 조건이다.**
> Claude는 description을 읽고 "지금 이 스킬을 호출해야 하는가?"를 판단한다.

세 가지 패턴 모두 **호출 상황(파일·작업 맥락)** + **필요한 정보 유형** + **cross-reference** 구조를 따른다.

### `_api` 패턴

```
`src/shared/api/{도메인}/` 또는 `src/entities/{도메인}/`를 작성·수정할 때,
{엔드포인트} API의 경로·파라미터·Request/Response 구조가 필요하면 호출한다.
도메인 타입·관계는 [[{도메인}_domain]], UI 흐름은 [[{도메인}_scenario]]를 호출한다.
```

### `_domain` 패턴

```
계층 무관하게 {Entity}가 무엇인지, {상태·플래그 필드}가 현실·시스템에서 무엇을 뜻하는지,
{관계·불변조건}이 무엇인지 알아야 할 때 읽는다.
`src/features/`와 `src/entities/` 모두에서 타입을 참조할 때 기준 문서가 된다.
API 명세는 [[{도메인}_api]], UI 흐름은 [[{도메인}_scenario]]를 읽는다.
```

### `_scenario` 패턴

```
`src/features/{도메인}/` 또는 `src/pages/{도메인}/`에서
{기능}의 UI 흐름·상태 전이·에러 처리·폼 로직을 구현·수정할 때 읽는다.
타입·불변조건·필드 값의 의미는 [[{도메인}_domain]], API 명세는 [[{도메인}_api]]를 읽는다.
```

## 바디 섹션 구조

| 섹션 | 필수/선택 | 포함 기준 |
|------|-----------|-----------|
| 한 줄 정의 | **필수** | 항상 |
| 출처와 확인 상태 | **필수** | 문서·API 버전/위치, 확정·관찰·미확정 구분. 출처가 없으면 미확정으로 기록 |
| 실행 계약 참조 | 코드 계약이 있으면 필수 | 스키마 파일과 export 참조. 타입 선언을 문서에 복제하지 않음 |
| API 명세 | **필수** (API 있을 때) | HTTP method별 필수 항목 규칙 참고 |
| 에러 응답 | **필수** (API 있을 때) | 확인된 케이스만. 없으면 `<!-- unconfirmed -->` 명시 |
| 핵심 제약사항 | **필수** | 항상. 없으면 `- 없음` 명시 |
| 필드 의미 | **필수** (`_domain`) | 의미가 자명하지 않은 필드의 값별 현실·시스템 의미 (아래 "필드 의미 작성 기준") |
| 도메인 구조 | 선택 | 엔티티 관계 2개 이상일 때 |
| 핵심 의사 결정 | 선택 | 비자명한 설계 판단이 있을 때 |
| 시나리오 / 처리 흐름 | **필수** (`_scenario`) | 성공 흐름 + 실패/에러 흐름 모두 |
| 실패 처리 | **필수** (`_scenario`) | 그 도메인의 실제 실패 표면에서 유도 (아래 "실패 흐름 작성 기준") |
| 화면 분기 근거 | **필수** (`_scenario`, 필드 값에 따라 화면이 달라질 때) | 아래 "필드 의미 기반 화면 분기 기준" |
| 화면 미사용 필드 | 선택 (`_scenario`, 화면 구현 후) | 화면이 구성된 뒤 응답 필드 중 화면에서 쓰지 않는 필드 (아래 "화면 미사용 필드 마킹 기준") |

**HTTP method별 API 명세 필수 항목**:

| Method | Query/Path | Request Body | Response | 에러 응답 |
|--------|------------|--------------|----------|-----------|
| `GET` | **필수** | 해당 없음 | **필수** | 확인된 케이스 |
| `POST` | 있으면 포함 | **필수** | 있으면 포함 | 확인된 케이스 |
| `PUT/PATCH` | 있으면 포함 | **필수** | 있으면 포함 | 확인된 케이스 |
| `DELETE` | 있으면 포함 | body 있으면 필수 | 있으면 포함 | 확인된 케이스 |

에러 응답이 제공되지 않은 경우:
```markdown
> ⚠️ unconfirmed: 에러 응답 구조 미확인.
```
> 공통 에러 포맷을 정의한 스킬이 **이 프로젝트에 실제로 존재할 때만** `[[그-스킬]]`로 링크한다.
> 존재하지 않는 스킬명(`[[error-contract]]` 등)을 예시대로 그대로 박아 넣지 말 것 — 끊긴 링크가 된다.

## 필드 의미 작성 기준 (`_domain` 전용)

타입 선언은 값의 모양만 알려준다. `_domain` 스킬은 각 필드의 값이 **현실 세계나 시스템에서
정확히 어떤 상태를 가리키는지**를 기록한다. 예를 들어 `status: boolean`이라면 `true`와 `false`가
각각 무엇을 할 수 있고 없는 상태인지, 누가 언제 바꾸는지, 바뀌면 어떤 처리가 달라지는지를 적는다.

**우선 기록할 필드**:

| 필드 유형 | 기록할 내용 |
|-----------|-------------|
| boolean 플래그 (`status`, `isActive`, `useYn` 등) | `true`/`false` 각각의 현실·시스템 상태, 전환 주체·시점, 전환 시 달라지는 처리 |
| enum·코드 값 | 값별 의미, 허용되는 전이 방향(있으면), 화면 표시명이 다르면 병기 |
| nullable·optional | `null`·누락이 뜻하는 상태 (미설정·해당 없음·처리 전 등 구분) |
| 시각 | 어떤 사건이 일어난 시각인지, 타임존·정밀도 |
| 수량·금액 | 단위, 범위, 포함·제외 기준 |
| 식별자·참조 | 가리키는 대상과 다른 엔티티와의 관계 |

`id`, `name`처럼 이름만으로 의미가 확정되는 필드는 생략한다.

**형식**:

```markdown
## 필드 의미

### {Entity}

| 필드 | 값 | 의미 (현실·시스템) | 근거 |
|------|----|--------------------|------|
| `status` | `true` | 로그인·주문이 가능한 계정. 관리자 승인 시 켜진다 | 협업자 확인 |
| | `false` | 로그인 시 403으로 차단되는 계정 | ⚠️ unconfirmed: 정지와 승인 대기를 구분하지 않는지 미확인 |
| `deletedAt` | `null` | 삭제되지 않은 레코드 | inferred: `OrderRepository` 조회 조건 |
| | 시각 | 소프트 삭제 시각. 목록 조회에서 제외된다 | inferred: 동일 |
```

**규칙**:

1. **이름에서 의미를 단정하지 않는다.** `status: true`를 "활성"으로 적으려면 그 상태에서 무엇이
   가능한지까지 출처로 확인되어야 한다. 확인되지 않으면 `⚠️ unconfirmed`로 표시하고
   `confidence.unconfirmed`에 등록한 뒤 협업자에게 확인할 질문을 결과 리포트에 남긴다.
2. **동어반복을 쓰지 않는다.** "활성 상태", "사용 여부"처럼 필드명을 되풀이하지 말고
   관찰 가능한 결과(할 수 있는 동작, 노출 위치, 처리 대상 여부, 연동 시스템의 반응)로 서술한다.
3. **근거를 구분한다.** 협업자 확인·문서는 확정, 코드에서 관찰한 동작은 `inferred`와 위치,
   모르는 값은 `⚠️ unconfirmed`로 적는다.
4. **의미는 실행 스키마가 있어도 기록한다.** 타입 중앙화 원칙은 타입 선언 복제를 막을 뿐이다.
   필드 의미 표에는 타입을 다시 쓰지 않고 값과 의미만 적는다.
5. `_api`·`_scenario`에서 같은 필드 의미가 필요하면 `[[{도메인}_domain]] 참고`로 처리한다.

## 필드 의미 기반 화면 분기 기준 (`_scenario` 전용)

화면이 필드 값에 따라 달라지면(노출·숨김, 버튼 활성·비활성, 뱃지·라벨, 필터 옵션, 허용 동작,
상태 전이) `_scenario`는 그 분기를 `[[{도메인}_domain]]`의 `## 필드 의미`에 근거해 서술한다.
`_domain`은 값이 **무엇을 뜻하는지**, `_scenario`는 그 의미 때문에 **화면이 어떻게 반응하는지**를 소유한다.

```markdown
## 화면 분기 근거

| 조건 (필드 = 값) | 의미 출처 | 화면 반응 | 근거 |
|------------------|-----------|-----------|------|
| `status = false` | [[user_domain]] 필드 의미 `status` | 목록에 "로그인 불가" 뱃지, 주문 버튼 비활성 | 기획 문서 v2 |
| `deletedAt != null` | [[user_domain]] 필드 의미 `deletedAt` | 목록에서 제외, 상세 진입 시 안내 문구 | ⚠️ unconfirmed: 상세 진입 가능 여부 미확인 |
```

**규칙**:

1. **의미는 `_domain`을 참조한다.** `_scenario`에서 값의 의미를 다시 정의하거나 다르게 해석하지 않는다.
   `_domain`에 의미가 없거나 `⚠️ unconfirmed`이면 그 분기도 `⚠️ unconfirmed`로 두고
   `_domain` 필드 의미 보강을 결과 리포트에 남긴다.
2. **의미에서 화면 반응을 지어내지 않는다.** "로그인할 수 없는 계정"이라는 의미가 확정돼도
   주문 버튼을 숨길지 비활성화할지는 기획·디자인 근거가 있어야 확정이다. 근거가 없으면 `⚠️ unconfirmed`.
3. **조건은 필드 값으로, 반응은 사용자가 관찰하는 결과로 쓴다.** "활성 사용자일 때"처럼 의미어만
   쓰지 말고 `status = true`를 함께 적어 테스트 데이터와 단언으로 바로 옮길 수 있게 한다.
4. given/when/then 흐름에서 상태 조건이 나오면 같은 표기(`필드 = 값`)를 쓰고 표의 행과 대응시킨다.

## 화면 미사용 필드 마킹 기준 (`_scenario` 전용)

API 응답이나 Entity에 있지만 화면에서 쓰지 않는 필드를 표시한다. 어떤 필드가 쓰이지 않는지는
화면 구성이 어느 정도 진행된 뒤에야 알 수 있으므로, **CREATE 시점에는 이 섹션을 만들지 않는다.**
화면 구현 후 UPDATE에서 코드 근거로 추가한다. 사용 여부는 화면에 속한 정보라서 `_domain`이 아니라
화면을 소유한 `_scenario`에 기록한다.

```markdown
## 화면 미사용 필드

> 기준: `src/pages/user/` · `src/features/user/` @ {커밋 또는 날짜}

| 필드 | 출처 | 미사용 사유 | 근거 |
|------|------|-------------|------|
| `createdBy` | [[user_api]] `GET /users` 응답 | 서버 감사용 | 기획 확인 |
| `legacyCode` | 동일 | 사유 미확인 | inferred: pages·features 참조 없음 |
| `lastLoginAt` | 동일 | 후속 화면(상세) 예정 | ⚠️ unconfirmed: 상세 화면 일정 미확인 |
```

**규칙**:

1. **코드로 확인한 뒤 마킹한다.** 화면 계층(`pages`·`features`, 프로젝트에 따라 `widgets`)과
   Entity 변환에서 필드 참조를 찾고, 참조가 없을 때만 미사용으로 적는다. Entity 변환에서 버려지는
   필드도 미사용이다. 검색 범위와 기준 시점을 섹션 머리에 적는다.
2. **사유를 구분한다.** 서버 내부용·감사용, 후속 화면 예정, 사유 미확인 중 하나로 쓰고 근거를 붙인다.
   협업자 확인 없이 "필요 없는 필드"로 단정하지 않는다.
3. **계약에서 지우지 않는다.** 미사용 필드도 `_api` 응답 명세와 실행 스키마에 그대로 둔다.
   마킹은 화면 범위의 사실이며, 계약 축소는 별도 판단이다.
4. **미사용 필드는 화면 분기 근거·테스트 단언 대상이 아니다.** 단, `_domain` 필드 의미는 다른 화면이나
   후속 작업을 위해 유지한다. 의미가 `⚠️ unconfirmed`인 미사용 필드는 확인 우선순위를 낮출 수 있다.
5. **화면이 바뀌면 갱신한다.** 필드를 쓰기 시작하면 행을 지우고, 기준 시점을 새로 적는다.

## 실패 흐름 작성 기준 (`_scenario` 전용)

`_scenario` 스킬은 성공 흐름과 실패 흐름을 모두 포함한다. 단, **실패 흐름은 그 도메인이
실제로 가진 실패 표면에서 유도한다.** 도메인마다 실패가 드러나는 방식이 다르다 —
mutation의 `onError` 토스트, 응답의 상태 필드, 비동기 잡의 상태 플래그, 폼 필드 검증 등.

> ⚠️ **외래 개념 오염 금지.** 특정 메커니즘(폴링 상태 플래그, 잡 상태, `overallStatus` 등)을
> **그 개념을 갖지 않은 도메인에 투영하지 않는다.** 이는 두 방향 모두 금지다:
> (1) 없는 메커니즘을 실패 흐름으로 지어내지 말 것,
> (2) "이 도메인은 `overallStatus`류를 갖지 않는다" 식으로 **부재를 외래 토큰의 이름으로
> 언급하지도 말 것**(부정 서술도 오염이다). 그 도메인이 **실제로 하는 것**만 서술한다.

먼저 코드에서 그 도메인의 실패가 어떻게 표면화되는지 확인한 뒤, 그 실제 경로만 적는다:

```markdown
## 실패 처리

### {기능명} 실패 시

```
{실패 트리거 — 그 도메인의 실제 신호}
  → UI: {실패 상태 표시 방법}  ⚠️ 미확인이면 unconfirmed
  → 재시도: {재시도 가능 여부·방법}  ⚠️ 미확인이면 unconfirmed
```

실패 흐름 정보가 없는 경우 `⚠️ unconfirmed`로 표시하고 `confidence.unconfirmed`에 등록한다.

## 작성 지침

1. **API 명세는 실제 JSON 그대로** — 사용자가 전달한 Request/Response Body를 가공 없이 포함.
   필드 의미가 불명확하면 이름에서 단정하지 않고 `⚠️ unconfirmed`로 표시한다.
   확인된 의미는 `_domain`의 "필드 의미" 섹션에 기록한다.

2. **한국어 + 영어 혼용** — 도메인 용어는 코드에서 사용되는 영어 식별자를 병기.

3. **UPDATE 시 기존 내용 보존** — 기존 섹션을 삭제하지 않는다. 새 정보를 추가하거나 변경된 부분만 수정.

4. **타입 중앙화 원칙** — 실행 스키마가 있으면 `_domain`은 해당 파일·export를 참조한다.
   코드 계약이 아직 없을 때만 동일 타입을 `_domain` 스킬 한 곳에 정의한다.
   `_api`와 `_scenario`에서 같은 타입이 필요하면 `[[도메인_domain]] 참고`로 처리.
   2.7단계(타입 권위 체크)를 통해 중복 정의를 사전에 차단한다.

5. **추측 금지 + unconfirmed 표기**:
   - 확인되지 않은 정보는 `⚠️ unconfirmed:` 인라인 주석 + frontmatter `confidence.unconfirmed` 에 등록.
   - 기존 body 내 `<!-- TODO -->` 는 `⚠️ unconfirmed:` 로 대체. (단, 레거시 스킬 호환을 위해 TODO도 허용)
   - **절대 금지**: 추측으로 필드값·동작을 채우는 것

6. **trio 완성 유도** — `_api`만 만들었다면 `_domain`·`_scenario`가 필요한지 사용자에게 확인.
   이미 존재하면 description의 cross-reference(`[[]]`)가 정확한지 검토.
   trio 중 누락된 스킬이 있으면 결과 리포트에 명시한다.

7. **횡단 관심사 분리** — 인증, 에러 포맷, HTTP 클라이언트 설정을 도메인 스킬에 기술하려 할 때,
   `[[common/concern-name]]` 참조로 대체하고 해당 common 스킬 생성을 제안한다.

## 자가 검증 체크리스트

SKILL.md 작성 완료 후 다음을 순서대로 확인한다. 결과 리포트에 PASS/FAIL 수를 포함한다.

### Frontmatter 검증

- [ ] `name`이 폴더명과 정확히 일치하는가?
- [ ] `name`이 `{도메인}_{타입}` 형식인가? (타입은 `_api` · `_domain` · `_scenario` 중 하나)
- [ ] `collaborators`에 TODO가 없는가?
- [ ] `description`이 타입에 맞는 트리거 패턴을 따르는가?
- [ ] `description`의 `[[링크]]`가 실제 존재하는 스킬명과 일치하는가?
- [ ] `confidence.unconfirmed`가 body의 `⚠️ unconfirmed` 항목과 일치하는가?

### 스킬명 검증

- [ ] 스킬명에 오타 패턴이 없는가? (flle, tpye, shcema 등)
- [ ] 폴더명 = frontmatter `name` = 사용자가 의도한 이름, 모두 일치하는가?

### Body 검증

- [ ] `## 한 줄 정의` 섹션이 존재하는가?
- [ ] `## 핵심 제약사항` 섹션이 존재하는가?
- [ ] API가 있다면 에러 응답이 명시되어 있거나 `⚠️ unconfirmed` 표기가 있는가?
- [ ] `_domain` 스킬이라면 의미가 자명하지 않은 필드(플래그·enum·nullable 등)의 값별 의미가 `## 필드 의미`에 근거와 함께 있는가? (동어반복·이름 기반 단정 금지)
- [ ] `_scenario` 스킬이라면 필드 값에 따른 화면 분기가 `## 화면 분기 근거`에 `필드 = 값`·`[[_domain]]` 의미 출처·화면 반응·근거로 적혀 있는가? (의미 재정의·근거 없는 화면 반응 금지)
- [ ] `_scenario`에 `## 화면 미사용 필드`가 있다면 검색 범위·기준 시점이 적혀 있고, 각 필드가 화면 코드에서 실제로 참조되지 않으며, 사유와 근거가 구분되어 있는가? (CREATE 시점에 추측으로 만들지 않음)
- [ ] `_scenario` 스킬이라면 실패 흐름이 **그 도메인의 실제 실패 표면**에서 유도돼 포함되어 있는가? (외래 개념 투영·부재 언급 금지)
- [ ] UPDATE 모드라면 기존 섹션이 삭제되지 않았는가?
- [ ] `⚠️ unconfirmed`가 있다면 frontmatter `confidence.unconfirmed`에 등록되어 있는가?

**API 명세 method별 검증**:

- [ ] `GET` API가 있다면 Query/Path Parameters와 Response가 모두 명시되어 있는가?
- [ ] `POST·PUT·PATCH` API가 있다면 Request Body가 명시되어 있는가?
- [ ] `DELETE` API가 있고 Body가 존재한다면 Request Body가 명시되어 있는가?
- [ ] 사용자가 제공하지 않은 Response를 추측으로 채우지 않았는가?

- [ ] 연결 스킬의 제약사항과 모순되는 내용이 없는가?

### trio 완성도
