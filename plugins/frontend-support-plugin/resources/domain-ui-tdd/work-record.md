# TDD 작업 기록과 검토 출력

기존 프로젝트의 작업 기록 위치를 우선 사용한다. 없으면
`docs/tdd/<domain>/<work-id>.md`에 이 형식으로 새 기록을 만든다. 기존 파일을
덮어쓰지 않고 같은 작업인지 확인해 갱신한다. 이 기록은 진행·근거·승인 인덱스이며
테스트의 기대 동작을 별도 명세로 복제하지 않는다. 플러그인 설치 경로에 쓰지 않는다.

```markdown
# 작업: {기능/범위}

- 요청: {명세화만 / 구현 포함}
- 단계: {diagnosing / contracts-ready / spec-authoring / review-pending / approved / implementing / specified / complete / blocked}
- 진입 상태: {기능별 신규 / 기존 / 변경}
- 기준선: {관련 실행 명령, 실행 시점, PASS/FAIL/미실행과 원인}
- 쓰기 범위: {계약 / 테스트 / 최소 골격 / 승인 후 구현 경로}

## 근거와 계약

| 근거 ID | 출처·버전·문서 위치 또는 API operation | 확정/관찰/미확정 | 연결 계약 파일 |
|---|---|---|---|

## 테스트 인덱스

| 요구사항 ID | 테스트 경로와 케이스 이름 | 근거 ID | 결과 분류 | 실패 단언·관찰값 또는 미실행 사유 |
|---|---|---|---|---|

## 실행 증거

- 명령·실행 시점·종료 코드·결과 요약·로그 위치:
- 실행한 코드/테스트 버전: {커밋 + 미커밋 diff/내용 해시 등 실제 실행 대상 식별}
- 논리 계층 검사 / 단위 / 통합 / 타입 검사 / 관련 회귀:
- 기존 실패·새 회귀·미실행 케이스:

## 검토 대상

- 계약·테스트·fixture·MSW 파일 목록과 각 파일의 SHA-256:
- 검토 diff 또는 보관된 스냅샷 위치:
- 아직 연결되지 않은 모듈·최소 골격:
- 충돌·특성화 동작·미확정 정책과 영향받는 요구사항:
- 승인 후 구현 범위:

## 승인 이력

| 요구사항 ID | 검토 버전/해시 묶음 | 개발자 응답 근거 | 승인/수정요청/보류 | 의미 변경 또는 승인 유지 사유 |
|---|---|---|---|---|

## 다음 작업

- 완료한 범위:
- 남은 구현·검토·환경 준비:
```

개발자 응답 근거에는 실제 메시지나 리뷰 참조를 남긴다. 에이전트가 승인자를 꾸미거나
무응답을 승인으로 해석하지 않는다. 승인 이후 파일이 바뀌면 diff로 의미 변경을 확인하고,
환경 수정이면 승인 유지 이유와 새 해시를 기록한다. 기대 동작 변경이면 해당 승인은 보류로
돌린다. 기록의 상태 문자열만 바꾸어 다음 단계로 넘어가지 않는다.

사용자에게는 단계, 테스트 결과 분류, 검토할 파일·diff 링크, 필요한 판단, 다음 작업만
간결하게 제시한다. 검토를 요청하며 멈출 때는 `domain-ui-tdd` 스킬과 이 워크플로의
개발자 검토 조건을 링크해 왜 승인이 필요한지 설명한다.
