# 도메인 UI TDD 단계

## 1. 진단 — 기능 단위로 진입점 선택

기존 작업 기록·사용자 변경·도메인 문서·소스·테스트·실행 설정을 먼저 읽는다.
존재하는 프로젝트 스킬 위치와 사용자 지정 문서 위치를 모두 조사한다.

| 기능 상태 | 작업 |
|---|---|
| 신규 | 도메인 지식과 논리 계약 준비 후 명세 테스트 작성 |
| 구현 완료·테스트 부족 | 기존 코드 보존, 계약 대조 후 누락 테스트 보강 |
| 구현·테스트 존재 | 신뢰도와 누락 검토 후 기존 테스트 재사용 |
| 기존 기능 변경 | 기존 동작 회귀 기준 확보 후 변경 요구만 RED로 명세화 |

변경 전 관련 테스트를 실행하고 기준선 실패를 기록한다. 환경이 없으면 미실행 이유를
기록한다. 프로젝트 전체 FSD 마이그레이션은 이 작업에 포함하지 않는다.
한 기능의 미확정 사항으로 독립적인 다른 기능까지 멈추지 않는다.

## 2. 계약 준비 — domain-knowledge-plugin 연계

`domain-contracts`의 원본 절차를 적용하고 근거·논리 계약 파일·미확정 사항·검증 결과를
전달받는다. 기존 스키마·service·Entity를 재사용한다. 신규 논리 계층은 `shared/api`와
`entities`까지만 구현하며 계약·변환·불변식 테스트와 타입 검사를 확인한다.
기존 계약 불일치가 발견되면 몰래 스키마를 바꾸지 않고 영향받는 테스트와 함께 검토한다.
UI 구현 전에 논리 계층을 먼저 준비하는 방식이다. 논리 계층까지 TDD를 요청받았다면
해당 계약 테스트도 먼저 RED를 확인하고 승인된 범위에서 구현한다.

## 3. 명세 테스트 — spec-first

[생명주기](../tdd/test-lifecycle.md)를 읽고 적용한다. 별도 UI 명세서 대신 테스트 코드에
요구사항 ID·근거·사용자 행동·기대 결과를 남긴다. 스키마·변환·도메인 불변식은 단위,
화면 행동과 HTTP 응답의 연결은 통합 테스트가 담당한다. 모든 케이스를 두 수준에
중복할 필요는 없다. 중요한 성공·실패·경계·복구 흐름을 명세에서 도출한다.

기존 테스트는 신뢰할 수 있는 것부터 재사용하고, 근거 없는 현재 동작은 특성화로
표시한다. 기존 기능의 PASS를 RED로 만들지 않는다. `test-reviewer`는 테스트 품질을
감사할 수 있으나 개발자의 업무 명세 승인을 대신할 수 없다.

## 4. 개발자 검토 — review-pending

[작업 기록](work-record.md)에 테스트·계약·fixture·핸들러의 파일 목록과 내용 해시,
테스트 diff, 케이스별 실행 결과, 미확정 정책, 구현 예정 범위를 준비한다.
실행 가능한 독립 범위의 작업을 마친 뒤 구체적인 검토 대상을 제시한다.

- 승인 요청은 “요구사항 ID와 해당 테스트의 기대 동작을 승인하는가”로 한정한다.
- 최초의 “기능 만들어줘”는 아직 작성되지 않은 테스트의 검토 완료가 아니다.
  반대로 현재 버전과 범위를 명시한 기존 승인은 반복 요청하지 않는다.
- 부분 승인은 요구사항 단위로 기록한다. 보류된 요구에 의존하는 기능은 구현하지 않는다.
- 특성화 테스트는 유지할 업무 동작으로 승인받은 뒤 회귀 명세로 전환한다.
- 테스트가 모두 PASS라도 근거 없는 현재 동작이 자동 승인되는 것은 아니다.

## 5. 구현 — approved → implementing

승인 범위·파일 버전이 현재와 맞는지 확인한 뒤 `features`, `pages`의 실제 동작을
구현한다. 기존 기능의 계약 수정은 별도로 승인된 범위만 적용한다.
작은 기능 단위로 목표 테스트 GREEN → 관련 회귀 실행 → 리팩터링 → 재실행한다.
기능의 화면 구성이 끝나면 도메인 `_scenario`의 화면 미사용 필드 마킹 갱신을 domain-skill-manager
절차로 요청하거나 작업 기록의 다음 작업으로 남긴다. 미사용 필드를 계약에서 지우지 않는다.
외부에서 기대 동작을 바꾸는 변경은 검토 단계로 돌리고, 환경 수정은 생명주기의
승인 유지 기준을 따른다. 테스트 작성자에게 구현까지 자동으로 떠넘기지 않는다.

## 6. 완료 또는 재개

- `specified`: 명세화만 요청한 범위가 검토 완료됐고, 실행 결과·남은 구현이 기록됨.
  기능 구현 완료로 보고하지 않는다.
- `complete`: 승인 범위의 단위·통합 테스트와 타입 검사·관련 회귀가 통과하고,
  그 범위의 미실행·충돌·예상 RED가 남지 않음.
- `blocked`: 환경·정보 부족으로 진행할 수 없는 기능과 필요한 조치를 기록.
- `review-pending`: 구체적인 산출물을 준비했고 개발자 검토가 필요한 상태.

재개할 때 기록만 믿지 말고 파일 해시·작업 트리·실행 환경·승인 범위를 대조한다.
실행 이후 관련 코드가 바뀌면 다시 실행한다. 명세 변경은 영향받은 요구만 재검토한다.
승인되지 않은 작업이나 남은 실패를 숨긴 채 도메인 전체 완료라고 보고하지 않는다.
