# integration-test-writer 요약 반환 형식

작성·실행이 끝난 뒤 메인 에이전트에 반환할 때 아래 형식을 그대로 사용한다.
격리 컨텍스트의 탐색 기록·시행착오 로그는 포함하지 않는다.

---

```
## 🔗 통합 테스트 작성 결과

**대상 흐름**: {페이지/사용자 흐름 이름 — 예: 로그인 화면, 주문 목록 조회→필터→상세}
**연결한 모듈**: {실제로 함께 렌더/연결한 컴포넌트·상태·로직·API 요청 코드}
**테스트 파일**: {test 경로 — src 미러}
**네트워크 경계**: MSW HTTP 핸들러 {성공 / 실패 / 지연 중 구성한 것}
**단언 소스**: {도메인 스킬 [[스킬명]]의 given/when/then·상태 전이 | 함수·API 계약}

**모드**: {verify / spec-first}
**작성 판정**: {완료 / 부분 완료 / 차단 — 기능 구현 완료와 구분}
**작업 기록**: {있으면 경로}

### 실행 결과
- 명령: `npx vitest run {파일}`
- 결과: {PASS n / FAIL n / 미실행 n} — {실제 실행 요약}
- 분류: {EXPECTED_RED / SPEC_CONFLICT / CHARACTERIZATION / BLOCKED / REGRESSION별 케이스}
- 증거: {실행 대상 버전·실패 단언·기대값·관찰값·로그 위치}
- 기존 테스트 재사용·새로 추가한 요구사항 ID와 근거:

### 커버한 흐름/케이스
- {케이스 1 — 어떤 사용자 상호작용(userEvent) → 어떤 관찰 동작(RTL 접근성 쿼리)을 어떤 근거로 단언했는지}
- {케이스 2 ...}

### 주의 / 후속 (있을 때만)
- {구현 버그로 의심돼 테스트로 노출된 부분 — 구현은 고치지 않았음}
- {도메인 스킬 신뢰도 의심 → domain-skill-reviewer 선행 권고}
- {대상 흐름이 모호해 확인이 필요한 질문}
```

- 단언은 "사용자가 관찰하는 화면 변화"(RTL 접근성 쿼리)에서 유도한 것만 적는다. 구현 세부(내부 상태 필드명 등)를 박제한 단언은 커버한 케이스로 보고하지 않는다.
- 전부 통과하고 후속 사항이 없으면 "주의 / 후속" 섹션은 생략한다.
- 통과시키려 단언을 무의미하게 약화시켰거나 MSW 대신 fetch 스터빙·API 클라이언트 목킹으로 연결을 끊은 경우, 그 사실을 반드시 "주의 / 후속"에 적는다.
