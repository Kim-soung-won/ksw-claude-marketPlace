# 단위 테스트 작성 규약 (vitest)

도메인 스킬과 함수 계약으로부터 **"코드가 하는 것"이 아니라 "해야 하는 것"을**
테스트하기 위한 규약이다. React + rsbuild + Module Federation, zustand +
react-query, FSD 구조 프로젝트에서 검증됐다.

> 이 문서는 **규약(지식)**이다. 실제 작성·실행은 `test-writer` 에이전트가 이
> skill을 로드해 따르고, 작성된 테스트의 감사(change-detector·약한 단언 적발)는
> `test-reviewer` 에이전트가 맡는다.
>
> 📎 실제 프로젝트에 커밋된 골드 예시(스킬 기반 스토어 테스트 / 계약 기반 검증
> 함수 테스트)는 같은 폴더의 [`examples.md`](./examples.md)에 있다. 단언을 어디서
> 어떻게 끌어올지 판단이 서지 않을 때 읽는다.

## 작업 모드 — 작성 전에 확인

[테스트 생명주기](../../resources/tdd/test-lifecycle.md)를 먼저 읽는다.
기본 `verify`와 명세 선작성 `spec-first`의 완료 조건, 기존 동작의 특성화,
유효 RED·환경 오류 구분은 이 리소스가 원본이다. TDD 전체 진행은
[domain-ui-tdd](../domain-ui-tdd/SKILL.md)를 사용한다. 기존 테스트를 먼저 읽고 재사용한다.
이하 명세/계약 우선 원칙은 유지하며, 근거가 없는 현재 동작의 기록에는 생명주기의
특성화 규칙을 적용한다. 프로젝트 설정은 실제 파일로 확인하며 세팅 완료를 가정하지 않는다.

## 최우선 원칙: 단언의 출처를 이원화한다

> **이 문서에서 가장 중요한 규칙이다.** 무엇을 단언할지는 구현 코드에서 베끼는
> 것이 아니라, 아래 두 출처 중 하나에서 **유도**한다. 구현을 그대로 박제하면
> 리팩터링마다 깨지는 change-detector가 되어 테스트의 가치가 사라진다.

테스트할 모듈의 근거를 먼저 분류한다. 스킬이 없다는 이유로 도메인 행위를 순수 로직으로 간주하지 않는다.

```
이 모듈에 대응하는 도메인 스킬(_scenario/_api/_domain)이 있나?
├─ 있다 (도메인 행위 모듈) ......... 스킬(명세)에서 단언을 유도  → 아래 A
├─ 없다 (순수 로직·유틸·검증) ...... 함수 계약에서 단언을 유도    → 아래 B
└─ 없다 (기존 도메인 행위) ......... 문서·요구 확인, 없으면 특성화 → 생명주기 원본
```

### A. 스킬 기반 — 도메인 행위가 있는 모듈

프로젝트의 도메인 스킬에서 기대 동작을 끌어온다. 특히 `*_scenario.md`의
**given/when/then · 상태 전이 · "핵심 제약사항"**이 테스트 케이스로 거의 1:1
매핑된다. `*_api.md`(입출력 계약)와 `*_domain.md`(도메인 규칙·필드 의미)도 함께 참조한다.
필드 값으로 분기하는 모듈(표시 라벨, 허용 동작 판정 등)은 `*_scenario.md`의 `## 화면 분기 근거`와
`*_domain.md`의 `## 필드 의미`에서 값별 기대 결과를 유도하고, 필드 이름에서 의미를 추측하지 않는다.

- **먼저 대상 모듈에 대응하는 도메인 스킬을 프로젝트에서 찾는다.** 이 도메인 스킬은
  `domain-skill-manager`가 만들어 프로젝트 경로의 `./.claude/skills/` 아래에 두는 산출물이다.
  ```bash
  git rev-parse --show-toplevel
  find "$(git rev-parse --show-toplevel)/.claude/skills" -name "SKILL.md" | sort
  ```
  대상 도메인과 매칭되는 `*_scenario`/`*_api`/`*_domain` 스킬을 Read해 단언의 1순위 근거로
  삼는다. 매칭되는 스킬이 없어도 업무 행위이면 문서·요구를 확인하고, 현재 동작만
  알 수 있으면 특성화로 기록한다. 순수 로직일 때만 아래 B(함수 계약)를 적용한다.
- 각 테스트 케이스 주석에 근거가 된 스킬 항목을 남긴다
  (예: `// scenario: "상태 관리 흐름" — step 0→1 전이`). 나중에 스펙이 바뀌면
  어느 테스트를 고쳐야 하는지 추적 가능해진다.
- **선행 게이트 — 낡은 스킬 = 낡은 테스트.** 스킬 기반 테스트를 쓰기 전에, 그
  도메인 스킬이 현재 코드와 어긋나지 않았는지 `domain-skill-reviewer`로 신뢰도를
  먼저 확인한다. 스킬이 낡았으면 테스트도 낡은 스펙을 박제한다.
- **실패는 노이즈가 아니라 스펙-구현 정합성 시그널이다.** 스킬에서 유도한 테스트가
  구현과 어긋나 실패하면, 둘 중 하나가 틀린 것이다 — 코드가 스펙을 어겼거나,
  스킬이 낡았거나. 선작성 범위의 미구현은 정상 RED 후보이며, 근거 충돌만 사람이 판정한다. 테스트를 통과시키려고 단언을
  구현에 맞춰 조용히 고치지 않는다.

### B. 계약 기반 — 대응 스킬이 없는 순수 로직

알고리즘 유틸·검증 함수처럼 대응 스킬이 없는 모듈은 함수의 **계약**에서 유도한다.

- **무게를 싣는 곳**: 시그니처, 반환 타입, JSDoc·코드에 명문화된 규칙, 타입·구조
  **불변식**(예: `isValid ⇔ errors.length === 0`).
- **최소화하는 곳**: 에러 **문자열 정확 일치**, private 분기의 세부 구현 —
  이런 단언은 계약 기반에서도 change-detector가 되는 위험 지점이다. 문자열은
  전체 일치 대신 핵심 부분 포함(`.includes(...)`) 수준으로, 문서화된 규칙에
  묶여 있을 때만 쓴다.

## 성공 입력만이 아니라 nullish·무효 입력 방어를 필수로 단언한다

> **성공 경로만 박제하지 않는다.** 함수가 `null`/`undefined`/빈 배열/누락 필드
> 같은 방어 경로 입력을 받았을 때 어떻게 행동해야 하는지도 계약·스킬에서 유도해
> 단언한다. 이 경계를 빼면 리팩터링이 아니라 실제 방어 로직의 회귀를 놓친다.

A(스킬 기반)·B(계약 기반) 어느 갈래든 아래를 **필수 케이스로** 포함한다.

### nullish·부분 입력 방어

- 함수가 `null`/`undefined`/빈 배열/누락 필드를 받았을 때 **throw하는지 안전
  처리(기본값·빈 결과)하는지**를 단언한다. 어느 쪽이 계약인지는 시그니처·JSDoc·
  불변식(B) 또는 대응 도메인 스킬의 핵심 제약·도메인 규칙(A)에서 유도한다 —
  "당연히 안전하겠지" 하고 넘기지 않는다.
- 설계상 throw가 계약이면 `expect(() => fn(null)).toThrow()` 수준으로 **throw
  여부만** 단언하고, 에러 메시지 문자열 정확 일치 같은 구현 결합 단언은 기존
  규약대로 최소화한다(불변식·throw 여부 위주).

### 검증 함수(zod schema.parse 등)는 유효·무효 둘 다

검증 함수는 유효 입력만 통과 확인하고 끝내지 않는다. **무효 입력까지** 단언한다.

- `schema.parse(...)`: 무효 입력에서 **throw**하는지
  (`expect(() => schema.parse(bad)).toThrow()`).
- `schema.safeParse(...)`: 무효 입력에서 `{ success: false }`를, 유효 입력에서
  `{ success: true }`를 주는지 양쪽.
- 여기서도 `error.issues`의 정확한 메시지 문자열 대신 **성공/실패 여부와 실패한
  경로(불변식)** 위주로 단언한다. 메시지 문구 정확 일치는 change-detector가 된다.

## 배치 컨벤션

루트 `test/`가 `src/`를 **미러링**한다.

```
src/shared/store/mcp/server-id-store.ts
  → test/shared/store/mcp/server-id-store.test.ts

src/entities/workflow/workflow/node-validator.ts
  → test/entities/workflow/workflow/node-validator.test.ts
```

프로젝트에는 이미 다음이 세팅돼 있다(새로 만들지 않는다).

- `vitest.config.ts`: `@/` → `src`, `@test/` → `test` alias,
  `test/**/*.{test,spec}.{ts,tsx}` 수집, 기본 `environment: "node"`, `setupFiles`.
- 루트 `tsconfig.json`의 `include`에 `test`가 포함돼 테스트도 함께 타입 체크된다.

> ⚠️ 테스트 전용 `tsconfig.test.json`을 별도로 만들지 않는다. `composite: true`로
> 분리하면 TS6307("전이적으로 import되는 모든 파일이 include에 있어야 함")로 깨진다.
> 루트 tsconfig의 `include`에 `test`를 넣는 쪽이 유지 비용이 낮다.

## 실행 환경 선택 — node vs jsdom

| 대상                 | 환경        | 방법                                               |
| -------------------- | ----------- | -------------------------------------------------- |
| 순수 함수, 검증 로직 | node (기본) | 추가 설정 없음. DOM 불필요                         |
| zustand 스토어       | node (기본) | `getState()`/`setState()`로 상태 검증. 렌더 불필요 |
| RTL 컴포넌트/훅 렌더 | jsdom       | 파일 **상단**에 `// @vitest-environment jsdom`     |

### RTL 주의 — 공용 렌더 하니스가 전제다

컴포넌트/훅 렌더 테스트는 `QueryClientProvider` · `LumenProvider` ·
`ToastProvider` · i18n · Module Federation 컨텍스트를 감싼 **공용 test-utils
렌더 하니스**로 렌더한다. 이 하니스는 모든 RTL 테스트가 공유하는 전제이므로,
순수 함수/스토어 테스트와 달리 "완전 독립·병렬"이 아니다. Provider를 매 파일에서
직접 조립하지 말고 공용 하니스를 경유한다.

> ⚠️ RTL에는 **인프라 문제가 단언 실패로 위장하는** 함정이 몇 가지 있다(자동
> cleanup 미등록, `userEvent.setup()`의 클립보드 교체, 접근명이 겹치는 닫기 버튼,
> `throwOnError` 훅). 단언을 무르게 고쳐 통과시키기 전에
> [`examples.md`](./examples.md)의 "RTL 실전 함정"을 먼저 확인한다.

## 검증 규율 — 작성으로 끝내지 않는다

테스트를 실제 실행하고 모드별 완료 조건을 판정한다. `verify`는 통과 확인,
`spec-first`는 케이스별 결과와 유효 RED/PASS·미확정·차단 근거 기록이 필요하다.
구현 결함·미구현으로 실패하면 작성자가 구현을 고치지 않고 원인을 반환한다.

1. 작성한 파일을 `npx vitest run <파일경로>`로 실행한다.
2. 실패하면 원인을 판정한다 — 테스트가 틀렸나, 스펙(스킬)이 낡았나, 코드가
   틀렸나. **테스트를 통과시키려고 단언을 무르게 고치지 않는다.**
3. 스킬 기반 테스트의 실패는 스펙-구현 정합성 시그널이므로, 조용히 넘기지 말고
   판정 결과를 사람에게 보고한다.
4. 타입은 루트 `tsconfig.json`의 `include`에 `test`가 들어 있어 함께 확인된다.

## 워크플로 체크리스트

응답에 이 체크리스트를 복사해 진행 상황을 추적한다.

```
테스트 작성 진행:
- [ ] 1. 대상 모듈 분류: `./.claude/skills/`에서 대응 도메인 스킬 탐색 → 도메인 명세(A) / 순수 계약(B) / 기존 동작 특성화 구분
- [ ] 2. (A인 경우) 대응 도메인 스킬을 domain-skill-reviewer로 신뢰도 확인 (선행 게이트)
- [ ] 3. 단언 출처 수집: (A) scenario given/when/then·상태 전이·핵심 제약 / (B) 시그니처·JSDoc·불변식
- [ ] 4. 배치 경로 결정: test/가 src/를 미러링
- [ ] 5. 환경 선택: 순수 로직·스토어=node / RTL=jsdom + 공용 하니스
- [ ] 6. 테스트 작성 (각 케이스에 근거 주석)
- [ ] 7. nullish/무효 입력 경계 케이스 포함: null·undefined·빈 배열·누락 필드에 throw인지 안전처리인지
        계약·스킬에서 유도해 단언 / 검증 함수는 유효·무효 입력 둘 다(parse throw·safeParse success:false),
        에러 문자열 정확 일치는 최소화
- [ ] 8. npx vitest run <파일>로 모드별 완료 판정 및 실패 분류
- [ ] 9. 실패 시 스펙-구현 정합성 판정 후 보고 (단언을 무르게 고치지 않기)
```

## 진행 톤

- 단언은 항상 **명세(스킬) 또는 계약**에서 유도한다. 구현 코드를 그대로 베끼지
  않는다(change-detector 금지).
- 스킬 기반 테스트 전에는 **스킬 신뢰도를 먼저** 확인한다(낡은 스킬 = 낡은 테스트).
- **성공 입력만 박제하지 않는다.** nullish·빈·누락 입력의 방어 동작(throw인지 안전
  처리인지)과 검증 함수의 무효 입력(parse throw·safeParse `success:false`)을 계약·
  스킬에서 유도해 함께 단언한다.
- 실행 증거와 모드별 판정 없이 완료로 보지 않는다. 실패는 판정 대상이지 통과시켜야 할 방해물이
  아니다.
