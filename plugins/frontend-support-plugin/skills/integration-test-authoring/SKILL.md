# 통합 테스트 작성 규약 (vitest + RTL + MSW)

여러 모듈을 **실제로 연결한 채** 페이지/사용자 흐름이 함께 동작하는지 검증하기
위한 규약이다. React + rsbuild + Module Federation, zustand + react-query, FSD
구조 프로젝트에서 검증됐다.

> **단위 테스트 규약과의 관계.** 같은 폴더군의 `test-authoring` 스킬이 vitest
> **단위(Unit) 테스트**(모듈 1개 격리, 함수 계약·도메인 스킬에서 단언 유도)를
> 다룬다면, 이 스킬은 그 대칭짝인 **통합(Integration) 테스트**를 다룬다. Testing
> Trophy 관점에서 통합 테스트는 컴포넌트+상태+로직+데이터 패칭+API 요청 코드를
> 함께 실행한 채 "페이지/흐름"이 사용자에게 보이는 대로 동작하는지를 본다.
> 작성 단위가 "모듈 하나"인지 "화면/흐름 하나"인지, 그리고 네트워크 경계를 MSW로
> 가로채는지가 두 규약을 가르는 기준이다. 두 규약 모두 **프로젝트의 도메인
> 스킬(`./.claude/skills/`)에서 기대 동작을 유도**하고 낡은 스킬 게이트를 공유한다
> — 단위 규약이 스킬 명세에서 단언을 끌어오듯, 이 규약은 스킬 계약에서 MSW 응답을,
> 스킬 시나리오에서 케이스를 끌어온다(아래 최우선 원칙 0). 이 구분은 본문에만
> 두며, 트리거 판단은 각 스킬의 description이 담당한다.
>
> 📎 실제 프로젝트에 커밋된 골드 예시(로그인 흐름 성공/실패, MSW 시나리오 전환)는
> 같은 폴더의 [`examples.md`](./examples.md)에 있다. 무엇을 실제로 연결하고
> 무엇을 MSW로 가로챌지 판단이 서지 않을 때 읽는다.
>
> 🔧 MSW 핸들러의 **정확한 v2 문법**(`http.*`·`HttpResponse`·`setupServer`·`server.use`·
> `delay`)은 별도 레퍼런스 스킬 [`msw-mocking`](../msw-mocking/SKILL.md)에 있다. 핸들러를
> 실제로 작성할 때 함께 읽어 v1(`rest`/`res(ctx)`) 문법 혼입을 막는다.

## 작업 모드 — 작성 전에 확인

[테스트 생명주기](../../resources/tdd/test-lifecycle.md)를 먼저 읽는다.
기본 `verify`와 명세 선작성 `spec-first`의 완료 조건, 기존 동작의 특성화,
유효 RED·환경 오류 구분은 이 리소스가 원본이다. TDD 전체 진행은
[domain-ui-tdd](../domain-ui-tdd/SKILL.md)를 사용한다. 기존 테스트를 먼저 읽고 재사용한다.
이하 명세/계약 우선 원칙은 유지하며, 근거가 없는 현재 동작의 기록에는 생명주기의
특성화 규칙을 적용한다. 프로젝트 설정은 실제 파일로 확인하며 세팅 완료를 가정하지 않는다.

## 최우선 원칙 0: 도메인 스킬을 MSW·단언의 1순위 근거로 삼는다

> **통합 테스트 퀄리티의 가장 큰 지렛대다.** 이 방법론을 쓰는 프로젝트마다
> 프로젝트 경로의 **`./.claude/skills/`** 아래에 `domain-skill-manager`로 만든
> 도메인 스킬이 구성돼 있다. MSW 응답과 화면 단언을 **구현이나 상상이 아니라
> 이 스킬에서 유도**하면, 모킹이 실제 서버 계약과 일치하고 테스트가 명세에 묶인다.

도메인 스킬은 세 형식이다.

| 파일 | 담긴 것 | 통합 테스트에서 쓰는 곳 |
| --- | --- | --- |
| `*_api.md` | 요청/응답 **계약**(URL·메서드·바디·응답 JSON 모양·상태코드·에러 응답 형태) | **MSW 핸들러의 요청 매칭·응답 본문** |
| `*_scenario.md` | given/when/then · 상태 전이 · 핵심 제약 · 화면 분기 근거 | **테스트 케이스(성공/실패/엣지)와 관찰 동작 단언** |
| `*_domain.md` | 도메인 규칙 · 필드 의미 | 경계·엣지 케이스와 **필드 값별 테스트 데이터**의 근거 |

### 1. MSW는 `*_api.md`의 계약에서 유도한다

MSW 핸들러의 요청 매칭(URL·메서드·쿼리·바디)과 **응답 JSON 모양·필드·상태코드·
에러 응답 형태**를 임의로 지어내지 않는다. `*_api.md`에 적힌 계약을 **그대로**
옮긴다. 그래야 실제 서버 계약과 일치하는 모킹이 되어, "테스트는 통과하는데
실서버에선 깨지는" 괴리를 없앤다. 성공 응답뿐 아니라 4xx/5xx **에러 응답의
형태**(에러 코드 필드·메시지 구조)도 계약대로 만들어야 에러 매핑이 제대로 검증된다.

### 2. 케이스와 단언은 `*_scenario.md`에서 1:1로 유도한다

어떤 흐름을 성공/실패/엣지로 나눌지와, 각 단계에서 화면에 무엇이 보여야 하는지는
`*_scenario.md`의 **given/when/then · 상태 전이 · 핵심 제약**에서 끌어온다. 시나리오
항목이 테스트 케이스로 거의 1:1 매핑된다. `*_domain.md`의 도메인 규칙은 경계값·엣지
케이스(빈 목록, 한도 초과, 권한 없음 등)를 만들 근거로 참조한다.

- **필드 값에 따라 화면이 달라지는 흐름은 값마다 케이스를 만든다.** `*_scenario.md`의
  `## 화면 분기 근거`의 각 행(`필드 = 값` → 화면 반응)을 케이스로 옮기고, MSW 응답에 그 값을
  넣어 화면 반응을 단언한다. 값의 의미는 `*_domain.md`의 `## 필드 의미`에서 확인하고,
  의미나 화면 반응이 `⚠️ unconfirmed`이면 확정 명세로 단언하지 않고 미확정으로 보고한다.
  분기 근거가 없으면 필드 이름에서 화면 반응을 추측하지 않는다.
- `*_scenario.md`의 `## 화면 미사용 필드`에 있는 필드는 화면 단언 대상이 아니다. MSW 응답에는
  `*_api.md` 계약대로 그대로 포함해 실제 응답 모양을 유지한다.
- 각 케이스 주석에 근거가 된 스킬 항목을 남긴다
  (예: `// scenario: "로그인 흐름" — 401 실패 시 에러 배너`, `// api: POST /auth/login 401 계약`,
  `// scenario 화면 분기: status = false → 주문 버튼 비활성 / domain 필드 의미: status`).
  스펙이 바뀌면 어느 테스트·핸들러를 고칠지 추적 가능해진다.

### 3. 선행 게이트 — 낡은 스킬 = 낡은 MSW/테스트

도메인 스킬을 근거로 쓰기 전에, 그 스킬이 현재 코드와 어긋나지 않았는지 확인한다.
낡은 `*_api.md`로 MSW를 만들면 **실서버와 다른 계약을 박제**하고, 낡은
`*_scenario.md`로 케이스를 만들면 낡은 스펙을 박제한다. 신뢰도가 의심되면 직접
판정하지 말고 `domain-skill-reviewer` 선행을 안내한다(단위 규약의 동일 게이트와
대칭). **스킬에서 유도한 테스트가 구현과 어긋나 실패하면**, 코드가 스펙을 어겼거나
스킬이 낡은 것일 수 있다. 선작성 범위의 미구현은 정상 RED 후보이며, 근거 충돌은
사람이 판정한다. 통과시키려고 단언·핸들러를
구현에 맞춰 조용히 고치지 않는다.

### 4. 대응 도메인 스킬이 없는 흐름

현재 구현에서만 확인한 동작은 생명주기 원본의 특성화로 기록하며 승인된 명세로 취급하지 않는다.

`./.claude/skills/`에서 대상 흐름에 맞는 스킬을 찾지 못했다면, API 경계 계약을
**실제 요청/응답 관찰이나 코드의 타입·API 클라이언트 시그니처**에서 최소한으로
유도한다. 지어낸 응답 모양으로 과신하지 않는다 — 확인된 필드만 계약으로 삼고,
불확실한 부분은 관찰로 좁힌다. (도메인 행위가 뚜렷한 흐름인데 스킬이 없다면,
`domain-skill-manager`로 스킬을 먼저 만들 가치가 있는 신호다.)

## 최우선 원칙 1: 내부는 실제로, 경계만 대체한다

> **이 문서에서 가장 중요한 규칙이다.** 통합 테스트의 가치는 "함께 붙여 놨을 때
> 실제로 도는가"에서 나온다. 내부 연결을 목으로 끊는 순간 그 가치는 사라진다.

한 흐름을 구성하는 모듈들을 **실제 구현으로 함께 실행**한다.

| 대상 | 통합 테스트에서 다루는 방식 |
| --- | --- |
| 컴포넌트(폼·버튼·목록) | 실제 렌더. RTL로 사용자처럼 조작 |
| 검증·변환 로직 | 실제 실행 (목 금지) |
| zustand 스토어 | 실제 스토어. 흐름 중 상태 전이가 화면에 반영되는지 관찰 |
| react-query 훅 | 실제 훅. 로딩/성공/에러 상태가 실제로 흐르게 둔다 |
| API 요청 코드(클라이언트 함수) | 실제 실행 — 직렬화·파싱·에러 매핑까지 돈다 |
| **네트워크 경계(HTTP)** | **여기만 MSW로 가로챈다** |

**대체는 오직 네트워크 경계에서, MSW(Mock Service Worker)로 HTTP 레벨에서만
한다.** MSW는 실제 요청이 나가는 지점에서 응답을 가로채므로, 요청 URL·메서드·
헤더·바디 직렬화와 응답 파싱·에러 매핑까지 **실제 코드가 그대로 돈다.**

### 지양 대상 — 연결을 끊는 목

다음은 "요청↔응답 처리" 연결을 끊어 통합 테스트를 사실상 단위 테스트로
퇴화시킨다. 통합 테스트에서는 지양한다.

- `global.fetch`/`axios` 인스턴스 스터빙 — 직렬화·파싱 경로가 통째로 죽는다.
- API 클라이언트 함수(`fetchOrders` 등) 목킹 — 요청 코드가 실행되지 않는다.
- react-query 훅 자체를 `vi.mock`으로 교체 — 로딩/에러 상태 흐름이 사라진다.

> 경계는 **HTTP 한 곳**이다. 흐름 안의 어떤 모듈을 목하고 싶어지면 먼저 "이게
> 정말 통제 불가능한 외부 경계인가, 아니면 내가 검증해야 할 내부 연결인가"를
> 묻는다. 답이 후자면 목이 아니라 MSW 응답 시나리오로 상황을 만든다.

### 네트워크 경계 vs 렌더 경계

위에서 "대체는 HTTP 경계 한 곳"이라 할 때의 경계는 **네트워크(HTTP) 경계**다.
이와 성격이 다른 두 번째 경계가 있다 — jsdom이 실제로 그려내지 못하는 **렌더
경계**다(canvas 차트=ECharts, 가상 스크롤=react-virtuoso, 파일 DnD=react-dropzone,
blob 다운로드, floating 포지셔닝 등의 leaf). 둘은 다루는 규칙이 다르므로 구분한다.

- **네트워크 경계(HTTP)** — MSW로만 가로챈다. API 클라이언트 함수·훅 목킹은
  요청↔응답 연결을 끊으므로 금지한다(위 규칙 그대로).
- **렌더 경계(jsdom 미지원 leaf)** — 그 leaf의 **시각화만 stub**하는 것은
  허용한다. 단 **거기로 들어가는 데이터 흐름은 실제로 유지**한다: leaf에 넘어간
  데이터와 역할(aria)을 관찰 단언하고, 픽셀·좌표·위치의 정확성은 E2E로 이관한다.

렌더 경계 leaf stub은 원칙 1의 "연결을 끊는 목 금지"의 **예외가 아니다.** 데이터
연결을 그대로 지키는 한에서 그리기만 대체하는 것이므로 같은 원칙(내부는 실제로)
아래 있다. leaf로 들어가는 데이터 흐름까지 stub으로 끊으면 그건 금지 대상인 목이다.

> 렌더 경계의 구체 대응 사다리·jsdom 한계 카탈로그·레시피(폴리필 / 하니스가
> 주입하는 목 컨텍스트 / leaf stub / 축소 / E2E 이관)는 `integration-test-writer`
> 에이전트의 [`rendering-boundaries.md`](../../resources/integration-test-writer/rendering-boundaries.md)에
> 있다. 이 스킬 본문은 개념 구분만 담고, 절차는 그 리소스를 따른다(본문은 얇게).

## 최우선 원칙 2: 단언은 사용자가 관찰하는 동작에서 유도한다

무엇을 단언할지는 구현 내부(상태 값·함수 호출 횟수)가 아니라, **사용자가 화면에서
관찰하는 것**에서 끌어온다. 입력 → 제출 → 응답에 따른 화면 변화를 본다.

- 검증 대상: 성공/실패 UI, 에러 메시지 노출, 리다이렉트, 로딩 스피너의 등장·소멸,
  목록의 채워짐·비워짐, 비활성/활성 전환.
- 쿼리는 **접근성 쿼리 우선**(`getByRole`, `findByRole`, `getByLabelText`). 사용자가
  화면을 인지하는 방식과 같아 구현 결합이 낮다. `data-testid`는 접근성 쿼리로
  도저히 잡히지 않을 때만.
- 비동기 응답 뒤의 변화는 `findBy*`/`waitFor`로 기다린다. 응답이 반영되기 전에
  단언하지 않는다.
- **change-detector를 만들지 않는다.** "스토어의 `step`이 1이 됐다", "`setUser`가
  1번 불렸다" 같은 내부 박제 단언은 리팩터링마다 깨지고 사용자 가치를 담지 못한다.
  같은 사실을 "화면에 무엇이 보이는가"로 바꿔 단언한다.

---

## 최우선 원칙 3: 작성 단위는 페이지/흐름이다

단위 테스트가 "모듈 1개"라면, 통합 테스트의 단위는 **사용자 흐름 하나**다.

- 예: "로그인 화면"(입력→제출→성공 리다이렉트 / 실패 에러 표시), "주문 목록
  조회→필터→상세 진입", "장바구니 담기→수량 변경→결제 진입".
- 한 흐름의 **성공 경로와 주요 실패 경로**(검증 실패, 4xx, 5xx, 지연/타임아웃)를
  같은 파일에 함께 담는다. 실패 경로 각각은 MSW 응답 시나리오로 만든다.
- 흐름의 진입점이 되는 페이지/화면 컴포넌트를 렌더의 루트로 삼는다. 하위 컴포넌트
  하나만 떼어 렌더하면 그건 통합이 아니라 컴포넌트 단위 테스트에 가깝다.

## 최우선 원칙 4: 성공 경로만 세우지 말고 실패·방어 경로를 관찰한다

> **성공 응답만 박제한 통합 테스트는 절반짜리다.** 이 프로젝트는 API 응답을
> zod 등으로 검증하고, **검증 실패 시 throw → 상위 ErrorBoundary가 잡아
> ErrorPage(에러 폴백)로 전환**하는 설계다. 이 방어 경로가 실제로 도는지까지
> 봐야 통합 테스트의 값어치가 산다.

한 흐름을 세울 때 다음 두 실패 모드를 **성공 케이스와 같은 파일에** 함께 담는다.

### 1. 스키마 검증 실패 → ErrorPage 전환

성공 응답만 MSW로 세우지 말고, **계약을 위반하는 응답**도 세운다: 필수 필드
누락·타입 불일치·기대와 다른 enum·nullable 아닌 필드의 `null`. 이런 바디를
받으면 zod 검증이 throw하고 화면이 ErrorPage로 바뀌어야 한다. 그 전환을 RTL
접근성 쿼리로 관찰 단언한다(에러 폴백 헤딩·문구가 `findBy*`로 뜨는지).

- 위반 바디는 `*_api.md`의 성공 계약을 **일부러 어긴 것**이므로, 근거 주석에
  어떤 계약을 어겼는지 남긴다
  (예: `// api: GET /orders 응답에서 필수 status 필드 제거 → zod throw`).
- 계약 위반 응답을 MSW로 만드는 문법은 아래 "MSW 규율"의 실패 시나리오와
  [`examples.md`](./examples.md)의 "실패·방어 경로 예시"를 본다.

### 2. null / undefined / 부분 데이터 경계

응답이 nullable 필드를 `null`로 주거나, 배열이 비었거나, optional 필드가
빠졌을 때 렌더·가공 로직이 JS 레벨에서 깨져 throw되는 경계를 살핀다.

- **어느 쪽이 맞는지는 도메인 스킬에서 유도한다.** 설계상 그런 입력이 ErrorPage로
  튕겨야 하면 ErrorPage 전환을 단언하고, graceful 처리(빈 상태·기본값)가 계약이면
  그 빈 상태 UI·기본 동작을 단언한다. 판단 근거는 `*_scenario.md`의 핵심 제약과
  `*_domain.md`의 규칙이다 — 상상으로 "당연히 빈 상태겠지" 하고 넘기지 않는다.
- 빈 목록·부분 데이터는 원칙 3의 "엣지 경로"와 이어진다. 성공·실패(스키마 위반)·
  엣지(null/빈)를 한 흐름의 분기로 함께 모은다.

## 배치 컨벤션

루트 `test/`가 `src/`를 **미러링**하는 규약을 그대로 승계하되, 작성 단위가
"흐름"이므로 흐름의 **진입점 컴포넌트 경로**를 기준으로 미러링하고 파일명에
`.integration`을 붙여 단위 테스트와 구분한다.

```
src/pages/login/LoginPage.tsx
  → test/pages/login/LoginPage.integration.test.tsx

src/pages/orders/OrderListPage.tsx  (조회→필터→상세 흐름)
  → test/pages/orders/OrderListPage.integration.test.tsx
```

- 단위 테스트(`*.test.ts(x)`)와 통합 테스트(`*.integration.test.tsx`)는 파일명으로
  갈린다. 수집 글롭(`test/**/*.{test,spec}.{ts,tsx}`)에는 둘 다 잡힌다.
- 흐름이 여러 페이지를 넘나들면(라우팅 포함) 흐름의 **시작 페이지** 경로에 둔다.
- `vitest.config.ts`·alias·`setupFiles`·타입 검사 범위를 실제로 확인한다. 기존 설정을
  재사용하고 부재 시 preflight 절차로 하네스에 준비를 요청한다.

## 실행 환경과 렌더 하니스

통합 테스트는 사용자 화면을 렌더하므로 **항상 jsdom**이다. 파일 **상단**에
`// @vitest-environment jsdom`을 둔다.

렌더는 `QueryClientProvider` · `LumenProvider` · `ToastProvider` · i18n · Module
Federation 컨텍스트를 감싼 **공용 test-utils 렌더 하니스**를 경유한다. 매 파일에서
Provider를 직접 조립하지 않는다. 통합 테스트는 라우팅·토스트·쿼리 캐시가 모두
살아 있어야 흐름이 실제로 도므로, 이 하니스가 특히 중요하다.

> ⚠️ QueryClient는 **테스트마다 새로 만든다**(하니스가 파일/케이스 단위로 격리된
> 클라이언트를 제공하거나 주입받게 한다). 캐시가 케이스 간에 새면 앞 테스트의
> 응답이 뒤 테스트에 잔류해 흐름 검증이 오염된다. 재시도는 테스트에서 끈다
> (`retry: false`) — 안 그러면 실패 경로 검증이 지연·불안정해진다.
>
> RTL 자체의 실전 함정(자동 cleanup 미등록, `userEvent.setup()`의 클립보드 교체,
> 접근명이 겹치는 버튼, `throwOnError` 훅)은 단위 규약과 공유한다.
> [`examples.md`](./examples.md)의 "통합 테스트 실전 함정"에서 MSW·흐름 고유의
> 함정과 함께 정리한다.

## MSW 규율 — 통합 테스트 고유의 핵심

MSW는 이 규약의 심장이다. 아래 규율을 지키지 않으면 통합 테스트가 서로 오염된다.

### 핸들러 배치와 재사용

- **기본(happy path) 핸들러는 공용 위치에 모아 재사용**한다(예:
  `test/msw/handlers/*`, 서버는 `test/msw/server.ts`). 흐름별 정상 응답은 여기서
  공유한다.
- **케이스별 예외 응답**(실패·지연·빈 목록)은 그 테스트 안에서
  `server.use(...)`로 **런타임 오버라이드**한다. 성공/실패/지연 시나리오 전환은
  전역 핸들러를 고치는 게 아니라 이 오버라이드로 만든다.

### 서버 라이프사이클과 상태 리셋 (오염 방지의 핵심)

```ts
import { beforeAll, afterEach, afterAll } from "vitest";
import { server } from "@test/msw/server";

beforeAll(() => server.listen({ onUnhandledRequest: "error" }));
afterEach(() => server.resetHandlers()); // 케이스별 server.use 오버라이드 해제
afterAll(() => server.close());
```

- `onUnhandledRequest: "error"` — 흐름이 예상 못 한 요청을 보내면 조용히 통과시키지
  말고 **실패로 드러낸다**. 어떤 요청이 실제로 나가는지가 통합 테스트의 관찰 대상이다.
- `afterEach`의 `resetHandlers()`가 **런타임 오버라이드를 되돌린다.** 이걸
  빠뜨리면 앞 케이스의 실패 응답이 뒤 케이스로 샌다.
- MSW 서버 상태뿐 아니라 **zustand 스토어·react-query 캐시도 케이스 간 리셋**한다
  (스토어 초기화, 새 QueryClient). 실제 연결이므로 상태도 실제로 잔류한다.

### 실패·지연 시나리오 만들기

- 4xx/5xx: `server.use(http.post("/api/login", () => HttpResponse.json({...}, { status: 401 })))`
  로 그 케이스에서만 에러 응답을 준다. 에러 매핑·에러 UI가 실제로 도는지 본다.
- 로딩 상태: 응답에 지연(`await delay(...)`)을 넣고, 지연 중 스피너가 보였다가
  응답 후 사라지는지 `findBy*`로 관찰한다.
- 계약 위반(스키마 throw): 성공 스키마를 **일부러 어긴** 바디를 준다 — 필수 필드
  누락·타입 불일치·`null`.
  `server.use(http.get("/api/orders", () => HttpResponse.json({ /* status 필드 누락 */ })))`.
  zod 검증이 throw → ErrorBoundary가 ErrorPage로 전환하는지 관찰한다(최우선 원칙 4).
  빈 배열·부분 데이터도 여기서 세워 빈 상태/에러 분기를 가른다.

## 검증 규율 — 작성으로 끝내지 않는다

테스트를 실제 실행하고 모드별 완료 조건을 판정한다. `verify`는 통과 확인,
`spec-first`는 케이스별 결과와 유효 RED/PASS·미확정·차단 근거 기록이 필요하다.
구현 결함·미구현으로 실패하면 작성자가 구현을 고치지 않고 원인을 반환한다.

1. 작성한 파일을 `npx vitest run <파일경로>`로 실행한다.
2. 실패하면 원인을 판정한다 — 흐름 구현이 틀렸나, MSW 응답 시나리오가 실제 API
   계약과 어긋났나, 단언이 화면이 아닌 내부를 보고 있나. **통과시키려고 단언을
   무르게 고치거나 흐름을 목으로 끊지 않는다.**
3. "Unhandled request" 에러가 나면 흐름이 예상 밖 요청을 보낸 것이다 — 핸들러
   누락인지, 흐름 자체의 버그인지 판정한다(통합 테스트가 잡아낸 실제 신호일 수 있다).
4. 타입은 루트 `tsconfig.json`의 `include`에 `test`가 들어 있어 함께 확인된다.

## 진행 톤

- **도메인 스킬(`./.claude/skills/`)이 MSW·단언의 1순위 근거다.** MSW 응답은
  `*_api.md` 계약에서, 케이스·단언은 `*_scenario.md`에서 유도한다. 쓰기 전
  신뢰도를 확인하고, 의심되면 `domain-skill-reviewer`를 선행한다.
- 내부 연결은 **실제로**, 대체는 **HTTP 경계 한 곳(MSW)**에서만. fetch/클라이언트
  함수/훅 목으로 연결을 끊지 않는다.
- 단언은 **사용자가 화면에서 관찰하는 것**에서 유도한다. 내부 상태·호출 박제 금지.
- 작성 단위는 **페이지/흐름**이다. 성공과 실패 경로를 함께 담는다.
- **성공 경로만 박제하지 않는다.** 계약 위반 응답으로 zod throw→ErrorPage 전환을,
  null·빈·부분 데이터로 방어 경계를 함께 단언한다. 튕겨야 할지 graceful 처리할지는
  `*_scenario` 핵심 제약·`*_domain`에서 유도한다(최우선 원칙 4).
- 케이스 간 **MSW 핸들러·스토어·쿼리 캐시를 리셋**한다. 오염된 통합 테스트는
  거짓 통과·거짓 실패를 만든다.
- 실행 증거와 모드별 판정 없이 완료로 보지 않는다. "Unhandled request"와 실패는 판정 대상이지
  무르게 넘겨야 할 방해물이 아니다.
