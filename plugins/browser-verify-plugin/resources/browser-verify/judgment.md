# 판단 지침

이 스킬에는 정해진 점검 순서가 없다. 무엇을 어떤 순서로 얼마나 깊게 볼지는 점검하는 쪽이 정한다.
이 문서는 그 판단을 돕는 생각의 틀이다. 규칙이 아니므로, 상황에 맞지 않으면 따르지 않고 이유를 보고서에 적는다.

## 계획은 변경에서 나온다

같은 절차를 모든 화면에 돌리지 않는다. 먼저 "이번 변경이 무엇을 깨뜨릴 수 있는가"를 생각한다.

- 변경 내역(diff, 변경 이력, 사용자의 설명)을 읽고 **위험 가설**을 세운다.
  예: "포커스 처리를 바꿨다 → 겹친 오버레이에서 포커스가 엉뚱한 곳에 갇힐 수 있다."
- 가설마다 **가장 싸게 확인할 방법**을 고른다. 수치 하나로 끝나는 것도 있고, 화면을 봐야 하는 것도 있다.
- 가설이 걸려 있는 화면부터 본다. 변경과 무관한 화면은 훑기만 하거나 건너뛴다.
- 변경 내역이 없으면(일반 점검 요청) 화면 구성을 먼저 읽고, 그 화면에서 가장 복잡한 상호작용부터 본다.

계획은 사용자에게 짧게 알리고 시작한다. 허락을 기다릴 필요는 없다.

## 계획은 바뀐다

점검 중에 얻은 정보로 계획을 고친다. 처음 계획을 끝까지 지키는 것이 목표가 아니다.

- **예상 밖의 결과**가 나오면 멈추고 그쪽을 판다. 스크립트의 클릭이 실패했다, 요청이 예상보다 많다,
  콘솔에 낯선 오류가 있다 — 이런 것이 재려던 항목보다 중요한 단서일 때가 많다.
- **같은 종류의 결함**을 하나 찾으면 같은 원인이 닿는 다른 곳을 찾아본다. 버튼 하나에 포커스 표시가 없으면
  원인이 전역 스타일인지 확인하고, 그렇다면 모든 버튼이 대상이다.
- **가설이 틀렸으면** 버린다. 문제가 없다는 것도 결과다.
- 시간과 비용이 한정돼 있으면 남은 가설 중 영향이 큰 것부터 본다. 보지 못한 것은 "확인 못 함"으로 남긴다.

## 도구는 부품이다

`scripts/` 의 파일은 절차가 아니라 꺼내 쓰는 부품이다.

- 그대로 쓰거나, 작업 폴더로 복사해 고치거나, 쓰지 않고 새로 써도 된다.
- 필요한 측정이 `lib.cjs` 에 없으면 그 자리에서 만든다. `page.evaluate` 로 화면에서 읽을 수 있는 값이면 무엇이든 근거가 된다.
- Playwright 가 맞지 않는 상황이면 다른 방법(브라우저 확장, DevTools 프로토콜 직접 호출, 사용자의 수동 확인 요청)을 쓴다.
- 새로 만든 측정이 다음에도 쓸 만하면 개선 기록에 남긴다. 그렇게 부품이 늘어난다.

`measurements.md` 는 지금까지 써 본 측정의 목록이다. 완전한 목록이 아니다.

## 놓치기 쉬운 것

정해진 절차가 없으면 빠뜨리기 쉬운 것들이다. 매번 하라는 뜻이 아니라, 계획을 세울 때 "이번에 이것이 해당하는가"를 스스로 묻는다.
건너뛰기로 했다면 보고서에 "측정하지 않음"과 이유를 적는다.

- **창 폭** — 한 폭에서 정상인 화면이 다른 폭에서 깨진다. 레이아웃에 닿는 변경이면 폭을 바꿔 본다.
- **움직임** — layout shift 와 애니메이션은 정지 화면에 보이지 않는다.
- **소비 앱의 전역 스타일** — 단위 테스트가 통과해도 실제 화면에서 덮인다.
- **재려던 것 밖의 모양** — 수치가 정상이어도 화면을 한 번은 봐야 보이는 것이 있다.
- **겹친 상태** — 다이얼로그 위의 확인 창, 팝오버 안의 메뉴처럼 두 기능이 만나는 곳.
- **데이터의 극단** — 빈 목록, 아주 긴 이름, 값이 없는 필드.
- **되돌아가는 길** — 열기뿐 아니라 닫기, 취소, 뒤로 가기.

## 막혔을 때

상황마다 답이 다르다. 아래는 생각할 방향이다.

| 상황 | 생각할 것 |
|------|-----------|
| 기대한 빌드가 아니다 | 점검해도 의미가 없다. 원인(설치 버전, 공유 설정, 캐시)을 좁혀 사용자에게 알린다 |
| 로그인이 안 된다, 권한이 없다 | 우회하지 않는다. 볼 수 있는 범위만 보고 나머지는 사용자에게 넘긴다 |
| 화면에 데이터가 없다 | 기간·필터를 바꿔 본다. 그래도 없으면 빈 상태 자체를 점검하고, 데이터가 필요한 항목은 "확인 못 함" |
| 조건이 맞아야 뜨는 화면이다(서버 요청, 특정 상태) | 조건을 안전하게 만들 수 있는지 본다. 데이터를 바꿔야만 한다면 만들지 않는다 |
| 눌러 봐야 알 수 있는데 누르면 바뀔 수 있다 | 코드를 읽어 확인 창이 먼저 뜨는지 본다. 확신이 없으면 누르지 않는다 |
| 스크립트가 계속 실패한다 | 화면의 실제 구조를 다시 읽는다. 가정(선택자, 여는 방법, 대기 시간)이 틀렸을 가능성이 높다 |
| 같은 방법을 세 번 시도했다 | 방법을 바꾼다. 다른 요소에서 접근하거나, 다른 값을 재거나, 스크린샷을 연다 |
| 결과를 해석할 수 없다 | 변경 전 빌드와 비교한다. 비교할 수 없으면 "판단 못 함"으로 적는다 |
| 점검 범위가 너무 넓다 | 사용자에게 우선순위를 묻거나, 위험 가설 순으로 자르고 자른 기준을 보고한다 |
| 요청에 없던 문제를 발견했다 | 보고한다. 고칠지는 사용자가 정한다. 점검을 멈추게 할 만큼 크면 바로 알린다 |

## 사용자에게 물을 때

판단은 스스로 하되, 아래는 사용자만 정할 수 있다.

- 서버 데이터를 바꿔도 되는지, 어디까지 눌러도 되는지
- 발견한 결함을 지금 고칠지
- 스크린샷·기록을 어디에 보관할지
- 범위를 줄여야 할 때 무엇이 중요한지

그 밖의 것(측정 방법, 순서, 스크립트 구성, 스크린샷을 열지 여부)은 묻지 않고 정한다.

### 결정을 요청할 때는 근거의 출처를 함께 준다

개발자에게 "고칠지", "어느 쪽으로 할지"를 물을 때, 판단에 쓸 수 있는 출처를 같이 언급한다.
출처는 결정을 대신하지 않는다. 개발자가 무게를 달 수 있게 하는 참고 자료다.

- 웹 표준에 관한 것이면 `modern-web-guidance`(GoogleChrome) 가이드를 언급한다. 가이드 id 와 해당 규칙을 짧게 인용하고,
  아래 세 가지를 함께 적는다.
  - 그 규칙이 무엇을 전제로 하는지(네이티브 `dialog`·`popover` 같은 요소를 쓰는 경우인지, 특정 기능을 쓰기로 한 경우에만 해당하는지)
  - 가이드에 적힌 브라우저 지원 상태
  - 이 프로젝트의 요구사항·규칙과 어긋나는 점이 있는지
- 프로젝트 규칙(설계 문서, 컴포넌트 문서)이나 사용자 요구사항이 근거면 그것을 언급한다.
- 근거가 화면에서 본 것뿐이면 그렇게 말한다. 출처를 지어내지 않는다.

가이드를 직접 조회하지 못했으면 "이 주제는 `modern-web-guidance` 에 가이드가 있을 수 있다" 정도로만 언급하고, 내용을 기억으로 옮기지 않는다.
가이드는 판정 기준으로 강제하지 않는다. 요구사항이 가이드와 다르면 요구사항이 우선이고, 그 사실을 함께 알린다.
