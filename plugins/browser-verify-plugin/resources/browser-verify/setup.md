# 시작하기

## 사용자에게 받아야 할 것

점검을 시작하기 전에 아래가 없으면 묻는다.

- 접속 주소와 로그인 계정
- 점검할 화면 목록과 기준(체크리스트, 변경 내역)
- 서버 데이터를 바꿔도 되는지, 안 된다면 어디까지 눌러도 되는지
- 시험할 빌드의 버전(로드 확인에 쓴다)

계정 비밀번호는 스크립트 실행에만 쓰고 문서·보고서·기록에 적지 않는다.

## 작업 폴더

스크립트 실행에 필요한 것(프로필, `playwright-core`, 스크린샷, 화면별 스크립트)을 한 폴더에 둔다.
세션 임시 폴더가 있으면 그 안에 만든다. 점검 대상 저장소 안에는 만들지 않는다.

임시 폴더는 재부팅·정리 때 사라질 수 있다. 사용자가 증빙이나 재사용을 원하면 어디에 보관할지 먼저 정한다.

## 준비 과정

제공된 스크립트를 쓰는 경우의 흐름이다. 환경이 다르면(이미 떠 있는 브라우저, 다른 운영체제, 다른 도구) 같은 결과에 이르는 다른 방법을 쓴다.

1. **환경 확인** — 접속 주소가 응답하는지, Chrome 이 설치돼 있는지 확인한다.
2. **준비** — `scripts/setup.sh <작업 폴더>` 로 `playwright-core` 를 설치한다(네트워크 필요).
3. **Chrome 실행** — `scripts/launch-chrome.sh <작업 폴더> [포트]`. 이미 떠 있으면 그대로 쓴다.
4. **접속과 로그인** — 주소로 이동해 몇 초 기다린 뒤 입력 칸 이름을 먼저 읽고, 그 이름으로 값을 넣는다.
   첫 화면이 비어 보이면 로딩이 끝나지 않은 것이다.
5. **빌드 로드 확인** — 점검하려는 빌드가 실제로 화면에 올라왔는지 확인한다. 아래 참고.
6. **점검** — 여기부터는 정해진 순서가 없다. [judgment.md](judgment.md) 를 따라 계획을 세운다. `scripts/survey.cjs` 와 `scripts/example-dialog.cjs` 는 출발점으로 쓸 수 있다.

모든 스크립트는 `BV_WORK=<작업 폴더>` 를 주고 실행한다. 화면별 스크립트는 `BV_LIB=<scripts 폴더>/lib.cjs` 도 준다.
`launch-chrome.sh` 에 기본값(9333)이 아닌 포트를 줬다면 Node 스크립트에도 `BV_PORT=<포트>` 를 같이 준다. 어긋나면 접속하지 못한다.
Chrome 이 흔한 위치에 없으면 `CHROME=<실행 파일 경로>` 를 주고 `launch-chrome.sh` 를 실행한다.

## 빌드 로드 확인

점검 전에 반드시 한다. 다른 빌드를 점검하면 결과 전체가 무의미하다.

- 화면 요소에 버전 표시(클래스·속성·전역 변수)가 있으면 그것을 읽는다. 클래스라면 `lib.classTokens(page, /^v\d+_/)`.
- 버전 표시가 없으면 이번 변경으로만 생기는 요소(새 `role`, 새 클래스)가 화면에 있는지 센다.
- 마이크로 프론트엔드에서는 호스트가 호환 버전을 제공하면 remote 의 빌드 대신 호스트 쪽 사본이 쓰일 수 있다. 버전이 둘 이상 보이면 각 화면이 어느 쪽을 쓰는지 확인한다.
- 기대한 빌드가 아니면 점검을 멈추고 사용자에게 알린다.

## 임시 Chrome 을 쓰는 이유

- 사용자의 평소 브라우저(로그인·확장·기록)와 분리된다.
- 한 번 띄운 브라우저에 스크립트가 매번 다시 접속하므로 로그인 상태가 유지된다.
- 창이 떠 있어 사용자가 진행을 볼 수 있다.
- Tab·Enter·방향키를 실제 키보드 이벤트로 보낼 수 있다.

점검이 끝나면 창이 로그인된 채 남아 있다는 것을 사용자에게 알린다.
