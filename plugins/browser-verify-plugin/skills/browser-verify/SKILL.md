# 브라우저 점검 (임시 Chrome)

사용자가 띄워 둔 웹 앱을 임시 Chrome 으로 열어 점검한다. 눈으로 보고 누르는 대신, 디버깅 포트로 접속한
스크립트가 화면을 조작하고 결과를 수치로 읽는다. 스크린샷은 수치로 답할 수 없는 것을 볼 때 연다.

**이 스킬에는 정해진 점검 순서가 없다.** 지켜야 할 것 몇 가지와, 꺼내 쓸 도구와, 판단을 돕는 문서가 있다.
무엇을 어떤 순서로 얼마나 깊게 볼지는 이번 변경과 화면을 보고 스스로 정한다.

- 판단을 돕는 생각의 틀: [judgment.md](../../resources/browser-verify/judgment.md) — 가장 먼저 읽는다
- 문서와 도구 목록: [리소스 인덱스](../../resources/browser-verify/index.md)

## 사용 조건

점검할 앱이 **이미 실행 중**이어야 한다. 이 스킬은 개발 서버를 띄우지 않는다.
주소가 응답하지 않으면 사용자에게 실행을 요청한다.

## 지켜야 할 것

상황과 무관하게 지킨다. 나머지는 모두 판단에 맡긴다.

1. **서버 데이터를 바꾸지 않는다.** 사용자가 명시적으로 허용한 범위만 예외다. 확신이 없으면 누르지 않는다.
   → [safety.md](../../resources/browser-verify/safety.md)
2. **어떤 빌드를 보고 있는지 모르는 채로 판정하지 않는다.** 기대한 빌드가 화면에 올라왔는지 확인하고,
   다르면 점검 결과를 내지 않는다. → [setup.md](../../resources/browser-verify/setup.md) "빌드 로드 확인"
3. **확인하지 않은 것을 통과로 적지 않는다.** "확인 못 함", "측정하지 않음"으로 적고 이유를 붙인다.
4. **근거를 구분해 보고한다.** 스크린샷 / 수치 / 주입 확인 / 합성 / 추측 중 무엇인지 밝힌다.
   → [report-format.md](../../resources/browser-verify/report-format.md)
5. **계정 비밀번호와 화면의 실제 데이터를 밖으로 내보내지 않는다.** 기록·저장소·외부 서비스에 적지 않는다.

## 일하는 방식

순서가 아니라 생각의 흐름이다. 상세는 judgment.md 에 있다.

- **변경에서 위험 가설을 세운다.** 이번 변경이 무엇을 깨뜨릴 수 있는지 생각하고, 가설이 걸린 화면부터 본다.
  모든 화면에 같은 절차를 돌리지 않는다.
- **화면을 읽고 나서 조작한다.** 코드만 읽고 세운 절차는 틀리기 쉽다. 구성을 먼저 읽는다.
- **가설마다 가장 싼 확인 방법을 고른다.** 수치로 되면 수치로, 안 되면 화면을 본다.
- **예상 밖의 결과가 나오면 계획을 바꾼다.** 클릭 실패, 낯선 요청, 콘솔 오류는 재려던 것보다 중요한 단서일 수 있다.
- **실패가 나오면 스크립트부터 의심한다.** 화면의 실제 상태를 다시 읽은 뒤 결함으로 판정한다.
  → [pitfalls.md](../../resources/browser-verify/pitfalls.md)
- **결함은 원인까지 본다.** 같은 원인이 닿는 다른 곳도 찾는다.
- **놓치기 쉬운 것을 스스로 묻는다.** 창 폭, 움직임, 소비 앱의 전역 스타일, 재려던 것 밖의 모양.
  이번에 해당하지 않는다고 판단했으면 건너뛰고 그 이유를 보고한다.

## 시작할 때 필요한 것

요청에 없으면 묻는다. 그 밖의 것은 묻지 않고 정한다.

- 접속 주소와 로그인 계정
- 무엇이 바뀌었는지(변경 내역, 기준 문서) — 없으면 일반 점검으로 보고 화면 구성에서 출발한다
- 서버 데이터를 바꿔도 되는지, 안 된다면 어디까지 눌러도 되는지
- 화면에 올라와 있어야 할 빌드 버전

## 도구

`../../resources/browser-verify/scripts` 에 있다(이 문서를 읽은 경로에서 절대 경로를 계산해 쓴다).
**절차가 아니라 부품이다.** 그대로 쓰거나, 작업 폴더로 복사해 고치거나, 쓰지 않고 새로 써도 된다.

| 파일 | 무엇인가 |
|------|----------|
| `setup.sh`, `launch-chrome.sh` | 작업 폴더 준비와 임시 Chrome 실행. 환경이 다르면 직접 띄워도 된다 |
| `lib.cjs` | 접속과 지금까지 써 본 측정 함수 모음. 필요한 측정이 없으면 만든다 |
| `survey.cjs` | 화면 구성을 읽는 한 가지 방법 |
| `example-dialog.cjs` | 다이얼로그 점검을 스크립트로 쓴 예시. 형식 참고용이다 |

```bash
bash "$SCRIPTS/setup.sh" "$WORK" && bash "$SCRIPTS/launch-chrome.sh" "$WORK"
BV_WORK="$WORK" node "$SCRIPTS/survey.cjs" <URL>
BV_WORK="$WORK" BV_LIB="$SCRIPTS/lib.cjs" node "$WORK/<직접 쓴 스크립트>.cjs"
```

- 작업 폴더는 세션 임시 폴더 안에 만든다. 점검 대상 저장소와 플러그인 폴더에는 쓰지 않는다.
- 포트를 바꿔 띄웠으면 `BV_PORT` 를 같은 값으로 준다.
- 측정 방법의 예: [measurements.md](../../resources/browser-verify/measurements.md).
  스크린샷을 찍고 여는 기준: [screenshots.md](../../resources/browser-verify/screenshots.md).

## 끝낼 때

- 바꾼 브라우저 상태(테마, 창 폭, 열린 창)를 되돌리고, 로그인된 창이 남아 있음을 알린다.
- 보고한다. 무엇을 보기로 했고 왜 그랬는지, 무엇을 건너뛰었는지를 함께 적는다.
- **배운 것을 남긴다.** 계획이 틀렸던 곳, 새로 만든 측정, 놓친 것을
  [improvement-log.md](../../resources/browser-verify/improvement-log.md) 에 추가한다.
  이 플러그인 저장소에 쓸 수 없는 세션이면 추가할 항목을 보고서 끝에 적어 사용자에게 전달한다.
  이 기록이 쌓이면서 도구와 문서가 늘어난다.

## 한계

이 방식으로 확인할 수 없는 것이다. "확인 못 함"에 적고 사람이 볼 항목으로 넘긴다.

- 실제 입력기(IME) 조합 — 합성 이벤트로만 확인할 수 있다.
- 스크린리더가 읽는 내용 — 속성 값은 읽을 수 있지만 낭독 결과는 알 수 없다.
- 주관적인 시각 품질 — 스크린샷을 열어 눈에 띄는 것만 전달한다.
- 띄울 수 없는 앱·모듈 — 본 범위를 적고, 한 앱의 결과를 전체의 안정성으로 쓰지 않는다.
